# 片头广告识别与裁剪：方案设计

> 状态：原型已跑通（`file-tool ad-cut`），本文记录的是**实测驱动的设计**，
> 不是设想。文中所有数字都来自 `/Volumes/P7000Z/R` 真实库（280 个视频）的测量。
> 模板库现有 **66 支**（34 支人工确认 + 32 支机器候选）。

## 1. 要解决的问题

视频开头插了一段广告，要把它切掉。目标是：

- **尽量不靠人工** —— 人工量正比于「广告种类数」，而不是「视频数」
- **越用越快** —— 见过的广告存成模板，新视频直接对模板库检索
- **不能弄坏原片** —— 磁盘只剩 168 GiB 而素材有几百 GB，失败必须可回滚

## 2. 三个决定方案走向的实测结论

### 2.1 片头广告是**共享素材**，不是每个视频各不相同

对全库 40 个视频做前 90 秒场景切换检测，发现这样一组时间戳：

```
26.716383, 26.74975, 30.276026, 32.044461, 33.345762, 33.712796
```

它同时出现在 `ABF-094`、`ACHJ-038`、`AIAV-003`、`AV-174`、`BBAN-433`、
`CAWD-660`、`DLDSS-313`、`DVMM-104`、`DVMM-072` 等**十几个毫不相关的作品**里，
**毫秒级一致**。

另有几个规模稍小的族：

| 族 | 公共切换点 | 成员数 |
|---|---|---|
| A | `26.716383, 26.74975, 30.276026, …` | 15+ |
| B | `1.157491, 2.458792, 2.825826, …` | 4 |
| C | `1.791458, 3.092759, 3.459793, …` | 3 |
| D | `0.0897564, 0.123123, 0.189857, …` | 3 |
| E | `1.491158, 47.427845, 74.121205, …` | 2 |
| F | `1.190858, 2.492159, 2.859193, …` | 2 |

**结论：识别不是机器学习问题，是指纹检索问题。** 广告种类数远小于视频数，
人工只需要为「种类」付出代价。

### 2.2 同一支广告在不同视频里被**重新编码**过 —— 精确哈希不可用

逐像素 md5 比对：

| 对比 | 逐像素 md5 相同帧 | 结论 |
|---|---|---|
| 族B `CLT-013C` vs `DVDMS-930` | 27 / 40（前 27 秒完全一致，之后分叉） | 同一素材 |
| 族A `ABF-094` vs `ACHJ-038` | 1 / 40（**第一帧就不同**） | 同一素材，被重新编码 |
| 族D `DCV-249` vs `DVMM-012` | 0 / 40 | 同一素材，被重新编码 |

同一支广告在族A 里连**逐像素**都对不上。所以匹配必须容忍重新编码。

改用感知哈希（dHash，64 位，汉明容差 6）后：

| 对比 | 覆盖率 | 连续匹配前缀 |
|---|---|---|
| 族A 内部 | 1.00 | 45 s |
| 族B 内部 | 0.60 | 27 s |
| 族D 内部 | 0.67 | 30 s |
| **跨族（全部 30 组）** | **0.00** | **0** |

**完全可分，没有任何交叉。** dHash 是整个方案的地基。

### 2.3 广告长度跨度极大，而且**片头内部就有多个硬切**

- 最短：`CAWD-660CX` 的黑底字幕卡，**10.8 秒**
- 最长：站方推广片，**186 ~ 235 秒**（多镜头轮播：码卡 → 电竞赞助 →
  直播平台推广 → 「票选前10大 最红女优」…）
- 有的视频前 90 秒**零场景切换**（`DNW-102A`、`DNW-106B`、`ORECO-640CX`）——
  纯场景检测会直接漏判

族A 的片头内部有五六个硬切：`26.7s / 30.3s / 33.7s / 57.4s / 104.8s / …`

**这一条推翻了「用画面突变点找边界」的思路。** 任何「找最大突变」「找第一个突变」
的启发式，在族A 上都会切在广告**中间**。所以：

> **边界只信人划出来的模板长度。** 帧间差异曲线只用来**佐证**，不参与定边界。

**「广告终点」的口径**（划每一刀之前先统一，否则各支各切各的）：

> 切在**站方推广片结束**的那一帧，**保留**片子自己的内容 ——
> 片厂 logo、黑底片名卡、免责卡都属于片子自身，**不算广告**，不许切掉。

举例：`ABF-094` 的推广片到 202 秒结束，203~204 秒是片厂 logo，
205 秒起是黑底片名卡 → 切点定在 **204 秒**，
把 logo 留着、把片名卡留着。`CLT-013C` 原先记成 193 秒，
就是把片子自己的片名卡和字幕卡（46 秒）误算成了广告，逐帧复核后改回 **147 秒**。

> **踩坑提醒：站方推广片比看上去长得多。**
> 第一次划边界时用的是「开头 180 秒」的全景拼图 —— 拼图只覆盖到 180 秒，
> 而推广片本身有 190~235 秒，于是 8 支模板的边界全部**定早了 40~70 秒**
> （记成 137s 的真值是 204s，记成 160s 的真值是 227s）。
> 裁出去一看，广告还剩一大半。
>
> **划边界用的观察窗口必须比广告长**，否则你量的不是广告的末尾，
> 是「拼图恰好截断的地方」。后来把窗口拉到 300 秒，边界才逐支核对正确。


### 2.4 关键帧结构：多数情况下可以无损流拷贝

片头区关键帧间隔（实测）：

| 文件 | 关键帧间隔 |
|---|---|
| `ABF-094` | 8.34 s |
| `CAWD-660CX` | 8.34 s（且 **10.81 s 正好是关键帧**） |
| `MBM-256` | 2.0 s |
| `ORECO-640CX` | 8.34 s |

好消息：**广告→正片的切换点经常正好是关键帧**（`CAWD-660CX` 的 10.81 秒既是画面硬切也是关键帧）。
这让「流拷贝」这个无损、几秒钟出结果的路径成为默认选择。

## 3. 系统架构

```
                     ┌─────────────┐
                     │  模板库 YAML │  rules/ad_templates.yaml
                     │  已知广告指纹 │  + 负样本
                     └──────┬──────┘
                            │ 比对
   视频 ──▶ ffprobe ──▶ 取片头指纹 ──▶ 判定 ──▶ CUT / REVIEW / NONE
              │            │           │
              │            │           └──▶ 未知族聚类（提示人工划一刀）
              │            │
              │            └──▶ 指纹缓存（重复扫描≈0 成本）
              │
              └──▶ 关键帧定位 ──▶ 流拷贝 / 重编码 ──▶ 临时文件 ──▶ 校验 ──▶ 原子替换
```

三个模块，各自职责单一：

| 模块 | 文件 | 职责 |
|---|---|---|
| 指纹层 | `file_tool/adcut/fingerprint.py` | 帧 → 64 位哈希 + 平均亮度 + 帧间差异 |
| 模板层 | `file_tool/adcut/templates.py` | 模板库的读写、学习、合并、负样本 |
| 决策层 | `file_tool/adcut/detect.py` `cut.py` | 判定、聚类、裁剪执行 |

外加两个支撑模块：`ffmpeg.py`（ffmpeg/ffprobe 调用封装）、`cache.py`（指纹缓存）。

## 4. 算法细节

### 4.1 指纹

每次取片头 300 秒的帧，缩到 32×32 灰度，对每帧算三个量：

> **为什么是 300 秒**：站方推广片的真实长度在 186~235 秒之间，
> 窗口必须装得下**最长**的那支（还要留几帧偏移余量），
> 否则判定层会因为「模板装不下窗口」而不敢下刀。

| 量 | 作用 |
|---|---|
| **dHash（64 位）** | 主证据。相邻像素大小关系，对重新编码/缩放稳健 |
| **平均亮度（0~255）** | 补 dHash 的洞：纯色画面的 dHash 恒为 0，「纯红卡」和「纯蓝卡」在哈希上完全一样。亮度差容忍 12 |
| **帧间差异 MAD** | 佐证。裁剪点处有硬切 → 模板记对了；没有 → 模板可能记错，降档 |

两帧「算同一画面」的条件：**dHash 汉明距离 ≤ 6 且 平均亮度差 ≤ 12**。

> **亮度分量必须进缓存。** 缓存命中时指纹是从 JSON 里拼回来的，
> 早先只存了 hashes/mad，brightness 拼不回来就是空列表，
> `match()` 里的亮度校验直接被整体关掉 ——
> 而且**没有任何报错**，只是匹配悄悄变宽松了。

### 4.2 匹配

模板假设出现在视频开头，允许 0~3 帧错位（有些片头前面挂着半秒黑场）。

- `prefix_len`：从起点开始**连续**匹配上的帧数
- `coverage`：整条模板被命中的比例（允许中间断开）

**裁剪点 = 模板长度 + 匹配偏移。** 偏移不能忘：广告未必从第 0 帧开始
（前面可能挂着站点 logo 或黑场），忘了就等于切早了几秒，广告尾巴留在片头。

**挑哪条模板**（多条都匹配上时）：

```
整条模板匹配上   >   人工确认过的模板   >   匹配得长   >   覆盖率高
```

「人工确认」排在「匹配得长」前面，是因为**模板长度就是裁剪点**：
一条人眼量过边界的模板和一条机器猜的模板都整条匹配上同一个视频时，
该信人眼那条。实测 `AKID-103` 的机器模板算出来是 230 秒，
人眼逐帧复核后确认也是 230 秒（原先记的 227 秒偏早 3 秒，已修正）。

> ⚠️ **这条优先级有一个副作用**：一条**已确认的短模板**会赢过一条**更长的候选模板**，
> 于是切点被压短（广告留着一截，但不会削到正片）—— 方向上是安全的。
> 代价是必须给这类视频**单独建一条属于它自己的模板**才能切干净（§5、§8 坑 11）。

### 4.3 置信度

```
整条模板全匹配上 (prefix ≥ len)      → 0.95
只匹配上一部分 (prefix < len)         → 0.45 + 0.5 × (prefix / len)
裁剪点处画面差异 ≥ 12（有硬切）       → +0.03
裁剪点处画面差异 < 4（无硬切）        → −0.12
模板不是人工确认的（机器学来的）      → 封顶 0.79
匹配不完整（prefix < 模板长度）       → 封顶 0.79
```

分档：`≥ 0.80` → 自动裁；`0.55 ~ 0.80` → 待人工确认；`< 0.55` → 没有广告。

「机器学来的模板封顶 0.79」这一条是**积累机制**的核心：
机器认出来的第一回只会让自己升级，**不会**让别的视频自动开刀；
被人确认过（或第二次被机器认出）之后才升格。

**「匹配不完整」单独封顶**，是因为分数公式区分不了两种情况：

- 这支视频的广告比模板**短** → 切过头，把正片也削了
- 这支视频的广告比模板**长** → 切不到底，广告还留着

实测 105/160 这种比例，公式算出 0.78，叠上硬切的 +0.03 正好 0.81，
**越过了 0.80 的自动裁剪线** —— 而那批视频的实际广告长度根本不是 160 秒，
切下去最多会削掉 55 秒正片。分数公式给不出区分，只能单独封顶。

### 4.4 未知族聚类


没命中任何模板的视频，按片头前 8 秒的指纹做聚类（近似匹配，不是精确相等）。

```
file-tool ad-cut cluster /Volumes/P7000Z/R
```

输出「这几组视频共享同一段还没认识的片头」，并指出每组的代表。
人工只要给**一个**代表划一刀，整组就都能自动处理了。

### 4.5 用「共享」自动定边界

前面所有关于边界的结论都指向「边界只能人划」。但在这个库里，
**站方推广片的数量级（70+ 个变体）已经超出了纯手工划边界的经济性**，
所以需要一个能给出**候选**边界的自动信号。

整套工具的立足点是：**片头广告是站方投放的共享素材，正片是每个发行版独有的。**
于是有两个可算的信号：

**跨片共享** —— 这一帧在别的视频里也出现过吗？

| 帧 | 同下标共享数 | 全库共享视频数 | 亮度 |
|---|---|---|---|
| 220（站方「票选前10大」卡） | 18 | 136 | 58.3 |
| 235（片名卡） | 1 | 4 | 4.7 |
| 245（正片） | 0 | 0 | — |

站方通用卡被**几十上百个**视频共用，而黑底片名卡只被两三个共用 ——
**共享者的数量**把两者分得干干净净，比「有没有共享」可靠得多。

**组内共享** —— 同一支推广片的不同发行版，内容逐帧完全一致（只是重新编码过）。
所以对同一组的两个视频：推广片区间每一帧都对得上，正片区间对不上。
于是「组内最后一个还对得上的帧号」就是推广片的终点 ——
**哪怕那张卡只在这一支推广片里出现过**，它在对上的时候也是组内对得上。

这个信号解决了跨片共享的一个硬伤：**变体独有的卡片**跨片检测不到，
共享段会在那里断掉（实测 `CLT-013C` 的推广片有 38 秒独有的卡片，
跨片检测把边界截在 147 秒，真值是 193 秒）。

> 但它也有自己的硬伤：**变体只有 1 个样本时，组内信号不存在**。
> 全库 76 个变体里，36 个有组内验证（141 个视频，边界可靠），
> 40 个是单例（40 个视频，边界只是**下界**，可能偏短）。
>
> 所以自动算出来的边界一律写进**候选模板**（`candidate`），
> 命中它的视频进人工确认档，不会自动开刀。
> **偏短只是留下广告，不会削到正片** —— 方向上是安全的。
>
> **这 40 个单例后来全部逐帧人工核验过了**（§8.2）。核验方法是
> 「大单格时间轴条带 + 每格的平均亮度/MAD 数值表」——
> 光看画面容易串行读错，**必须配数值**。
> 核验完发现：其中 8 支的推广片**共享段之后还跟着一段本片专属广告卡**，
> 跨片检测原理上就发现不了（共享数恒为 1），只能人眼核出来，
> 最后给它们单独建了 8 支「独有」模板（tpl-0059 ~ tpl-0066）。

配套脚本（一次性工具，不是产品功能）：

```bash
# 预热指纹缓存（窗口从 200s 扩到 300s 后要重算一遍，约 18 分钟）
PYTHONPATH=. .venv/bin/python scripts/warm_adcut_cache.py /Volumes/P7000Z/R 300

# 算出每个视频的广告长度（跨片共享）
PYTHONPATH=. .venv/bin/python scripts/find_ad_boundaries.py /Volumes/P7000Z/R 300

# 按「整条推广片一致」分变体，并给出组内验证过的边界
PYTHONPATH=. .venv/bin/python scripts/group_ad_variants.py  /Volumes/P7000Z/R

# 批量写进模板库（人工确认的 8 支用已核对过的边界，其余写成候选模板）
PYTHONPATH=. .venv/bin/python scripts/bootstrap_ad_templates.py /Volumes/P7000Z/R

# 诊断：看某支推广片每一帧被多少个视频共享（用来分辨「站方卡」和「片名卡」）
PYTHONPATH=. .venv/bin/python scripts/probe_shared.py /Volumes/P7000Z/R AKID-103/AKID-103.mp4
```

## 4.6 一条模板记不住「这支广告多长」—— 逐文件边界表

§2.3 讲的是「广告长度跨度极大」，但那说的是**不同广告之间**。
2026-11-09 的复核挖出更麻烦的一层：**同一支广告在不同片子里长度就不一样**。

### 现象

站方推广片是**多卡片轮播**（手机画面 → 二维码 → 票选前10大 → 游玩 → 百家樂 …），
每张卡片 4~8 秒。**每支片子插的卡片数量不一样**，广告总长跟着变：

| 模板 | 成员 | 各自真实的广告终点 |
|---|---|---|
| `tpl-0018`（gamebb 变体） | DVMM-012 / dvdms-00300a / dvdms-00300b / sdmu-00877b | 319 / 319 / 320 / 329 |
| `tpl-0017` | MIAA-954C / MIDV-465C / SDMM-120C / SDMM-126C | 291 / 291 / 291 / 291 |
| `tpl-0016` | HODV-21651 / KAGP-214A / NHDTB-623A | 275 / 227 / 227 |

模板长度只有**一个**数，套上去必然切错 —— 实测按模板长度裁，
最多会留下 **53 秒**广告尾巴（`SDMM-102`），或者反过来切进正片。

### 为什么「跨片共享自动推断」会固化这个错误

`find_ad_boundaries.py` 用「跨片共享」反推广告长度。但共享只保证
**前 N 秒是同一批素材**，管不到第 N 秒之后各片子还插了几张卡片。
所以自动推断出的长度对**同族里最短的那个**成立，对其余的都偏早。

更糟的是 `scan` 的默认窗口是 300 秒：当初给这几族做推断时，
广告还没播完就被窗口截断了，于是生成了**长度正好 300** 的模板 ——
那不是广告长度，是**观察窗口的长度**。实测 71 个待确认文件里
有 24 个用的就是这种模板。

### 解法：边界表覆盖模板长度

`rules/ad_boundaries.yaml` 逐个文件记下人工核验过的广告终点，
`detect.py` 命中时用它替代模板长度算出的裁剪点：

```
cut_at = 人工核验边界（若该文件在表里）
       = offset + template_len  （否则，走原来的推断）
```

人工边界一命中，判定直接升到 `CUT`、置信度 1.0，
并且**不再受「硬切 / 无硬切」启发式的影响** —— 边界是量出来的。

只写**确实逐帧核过**的文件；没核过的宁可没有，也不要写错的。
截至 2026-11-09 共录 **71 条**：逐帧核验过的 182 支里，
有 71 支的真实切点与模板长度对不上（同族广告插的卡片数不同），
用边界表钉死；其余 111 支模板长度本身就是真值，直接用模板。

### 核验方法：必须逐帧精确抽帧，不能用滤镜流水线

这一节是本轮返工量最大的一条结论，单独拎出来说。

核验广告边界的第一版做法是**抽帧拼图**：`-ss X -t N -vf fps=1` 拉一段出来，
拼成大图，人眼一格一格看「哪一格从广告变成正片」。看着很合理，
但**抽出来的帧和它标注的时间对不上**。

根因在这批文件的容器元数据上：`start_time = 0.023023`（音频轨偏移），
而且关键帧稀疏 —— 有的片子 10 秒才有一个关键帧。`-ss` + `-t` + `fps=1`
这三个滤镜串起来时，**输出流的时间轴是重新起算的**，
它跟源片的时间戳对不上号。实测同一句 `-ss 154`：
在 `SSIS-518C` 取到的是 140 多秒的内容，偏差可达 **10 秒**。

偏差是**逐文件**的，所以它不会自暴露 —— 每支片子错的方向和幅度都不一样，
拼图看起来永远「合情合理」。用它核出来的 182 支里有 **40 支切点错了**：
25 支早 1 秒（广告尾巴没裁干净），11 支晚了 7~48 秒（把厂牌片头也裁掉了）。

正确做法是**逐帧精确抽帧**，一次一帧，输出帧数固定为 1：

```bash
# 精确取第 154 秒那一帧 —— 输出时间轴就是源片时间轴
ffmpeg -ss 154 -i INPUT.mp4 -frames:v 1 -y /tmp/frame.png
```

（已验证输入 seek 与输出 seek 结果一致，`-ss` 放 `-i` 前面即可。）

`ad-cut sheet` 走的仍是滤镜流水线 —— 它是**粗找分界**的工具，
用来快速定位「广告大概在 200~320 秒之间」，然后用精确抽帧定终值。
两者不能互换。

### 厂牌片头不算广告

站方推广片之后、正片之前的那段黑底作品简介卡 / 免责卡 / 厂牌 logo
（MOGUOY 开场、OCCN 免责声明、`マジックミラー号` 卡、狗头卡、演员档案卡…）
按 §5 的口径**保留**。分类口径：

- **带站点二维码 / 站点 logo 的推广卡** → 站方广告，裁掉
- **黑底白字的作品简介 / 免责 / 厂牌 logo 卡** → 厂牌片头，保留

所以表里 `cut_at` 记的是**站方广告的终点**，
`site_ad_end` 记的也是同一个数；两者的差值就是被保留的厂牌片头长度。

## 5. 人工介入模型
这是整个设计里最要紧的一环。人工量正比于**广告种类数**：

```
第 1 次：库是空的，cluster 列出所有未知片头族
         人工给每族挑一个代表，量出广告结束时间 → learn
         → 这一族的全部视频立刻变成「可自动裁」

第 2 次：新库带来的新视频里，绝大多数自动命中
         只有**新出现的广告创意**才需要再划一刀

第 N 次：人工介入次数 ≈ 期间新增的广告种类数（很少）
```

`learn` 会自动判断「这支广告是不是已经有了」：
连续匹配 ≥ 85% 且长度差 ≤ 2 帧 → 合并进已有模板（`samples` 递增）；
否则新建一条。

**长度差超过 2 帧就分开建模板**，因为同一档节目换了新片头时，
前 3 秒一样、后面不一样 —— 混在一起会把模板拉长，
匹配时连续段提前断掉，裁剪点会落到广告中间。

### 改边界用 `--replace`，它同时也是「人工确认」的标记

```bash
file-tool ad-cut learn VIDEO --end 147 --replace tpl-0044
```

`--replace` 覆盖已有模板的边界，**保留 id 和样本计数**，并且
**把状态从 `candidate` 改成 `confirmed`**。这正是我们要的语义：
「这条边界是人眼量过的」。

> ⚠️ **`learn` 的自动合并会吃掉新建模板的机会。**
> 想给一支视频单独建模板时，如果库里已有一条前缀相同、长度只差 ≤ 2 帧的模板，
> `learn` 会**合并**进去而不是新建。
> 解法是两步：先用 `--end 100`（明显偏短）新建一条占位，
> 再用 `--replace` 把边界改到真值。占位长度与目标差得够远，就不会触发合并。

### 模板选择优先级的副作用：confirmed 的「短模板」会压掉 candidate 的「长模板」

模板选择的优先级是（§3.3）：

```
整条匹配上   >   人工确认过的模板   >   匹配得长   >   覆盖率高
```

于是会出现这种局面：某支视频的广告实际是 **230 秒**，
但库里有一条人工确认过的 **147 秒** 模板（属于另一个族）前缀完全吻合，
它就会被选中 —— 切点被**压短 83 秒**，广告剩一大截。

这不是 bug，是「边界只信人工标注的模板长度」这条铁律的必然结果。
处理办法只有一个：**给这类视频单独建一条属于它自己的模板**，
让它在自己的长度上整条匹配上，优先级第一档就赢了。

实测这一轮因此给 **9 支视频各自补了专属模板**，
修正了 14 支视频的切点。
反过来看，这个副作用是**安全方向**的：压短只会留下广告，不会削到正片。

### 负样本

`ad-cut reject VIDEO --end 12 --reason "这里没有广告"` 记一条负样本。
作用是抑制误切：片头本来就是静止画面时（黑场、站点 logo 动画），
dHash 有可能撞上某个模板；负样本让这类误报在下一轮被挡下来。

## 6. 裁剪执行语义

### 6.1 原地替换，绝不另存

磁盘只剩 168 GiB，素材几百 GB —— 另存一份再删是不可能的。
但直接「输出新文件 → 删原片」，中途失败就两头都没了。

所以顺序固定：

1. 裁到**同目录下的临时文件** `xxx.adcut-tmp.mp4`（同卷 → rename 原子）
2. 校验：文件大小、视频轨在、音频轨在（原片有的话）、时长 ≈ 原时长 − 裁剪点
   （容差 2.5 秒 + 原片 1%）
3. 校验通过才 `os.replace()` 顶掉原片（并保留原权限）

**任何一步失败：临时文件删掉，原片原封不动。**

### 6.2 流拷贝 vs 重编码

耗时差一个数量级：流拷贝一个 10 GB 的片子几秒钟，重编码几十分钟。

选择规则：

1. 切割点**之后**最近的关键帧，距离 ≤ `--max-snap`（默认 2 秒）→ 流拷贝
   （广告切得干干净净）
2. 否则看切割点**之前**最近的关键帧，距离 ≤ `--max-snap` → 流拷贝
   （会留一截广告尾巴，但快几十倍）
3. 都不满足 → 重编码，切在精确帧上（`--accurate` 可强制）

实测 `CAWD-660CX`：模板裁剪点 11.0 秒 → 吸附到关键帧 10.81 秒
（偏移 −0.19 秒）→ 流拷贝，1.6 GB 的片子几秒完成，
结果时长 7096.306 秒（期望 7096.307），首帧已是正片。

### 6.3 字幕

R 库实测**没有外挂字幕**（只有封面 jpg），所以当前不自动偏移时间轴。

但检测到同名外挂字幕时会**告警**：视频前 N 秒被切掉，
字幕还按原来的时间轴走，内容会整体错位。
接口已预留（`detect._subtitle_note`），后续补偏移模块即可。

## 7. 性能

| 操作 | 耗时 |
|---|---|
| 取片头 300 秒指纹（1080p） | 2 ~ 10 s / 视频 |
| 关键帧探测（前 300 秒） | ~1.5 s / 视频 |
| 模板匹配（66 条模板 × 300 帧） | ~20 ms |
| **重复扫描（命中指纹缓存）** | **~15 s / 280 个视频**（含 ffprobe 遍历；纯匹配约 4 s） |

缓存键包含**文件大小和修改时间** —— 文件被换掉后指纹自动失效重算。
缓存按平台惯例放在 `~/Library/Caches/file-tool/adcut`（Windows: `%LOCALAPPDATA%`）。

> 窗口从 180 秒拉到 300 秒是有代价的：冷扫描从 25 分钟变成 **18 分钟**
> （实测 280 个视频，6 并发）。换来的是模板能装得下最长的那支推广片
> （模板库现有 300 秒的候选模板、282 秒的确认模板），
> 判定层不会因为「模板装不下窗口」而拒绝下刀 —— 这笔买卖很划算。

「越来越快」有两个含义，都实现了：

1. **人工越来越少** —— 模板库越全，需要划的刀越少
2. **机器越来越快** —— 指纹缓存命中后重复扫描几乎零成本

### 怎么把 182 支逐帧核验出来

核验的难点不是「看画面」，而是**看准**。第一版用 5×4 / 5×2 的小格拼图读图，
结果串行 —— `MHAR-10C`、`DVMM-070`、`SSIS-518C`、`SDDE-553` 等支的边界
都误判了 1~2 秒。

改成 **512px 单格 + 3 列条带 + 每格标注「时间 / 平均亮度 / MAD」** 之后，
误差消失。数值（来自指纹缓存）比目测可靠得多：
亮度骤降说明进黑场、MAD 骤增说明画面硬切，两者互相印证。

> 但这一版本身也是错的 —— 它用的是 `fps=1` 滤镜流水线，
> 抽出来的帧和标注的时间对不上（§4.6）。**最终定案是逐帧精确抽帧。**

核验流程固定成三步：

```bash
# 1) 先看数值：打印缓存指纹的逐秒 brightness / MAD / dHash，定位候选边界
PYTHONPATH=. .venv/bin/python scripts/curve.py /Volumes/P7000Z/R/MHAR-10C/MHAR-10C.mp4 140 160

# 2) 再看画面：逐帧精确抽帧，逐格确认「广告 → 正片」
#    注意必须是 -frames:v 1 精确抽帧，不能用 -ss X -t N -vf fps=1（§4.6）
ffmpeg -ss 152 -i /Volumes/P7000Z/R/MHAR-10C/MHAR-10C.mp4 -frames:v 1 -y /tmp/f152.png

# 3) 把真值写回边界表（逐文件钉死切点）
PYTHONPATH=. .venv/bin/python scripts/apply_verified_cuts.py \
    /Volumes/P7000Z/R rules/ad_templates.yaml rules/ad_boundaries.yaml
```

一条经验：**数值定候选，眼睛定终值。** 数值负责把搜索范围从 300 秒缩到几秒，
眼睛负责做最后那 1~2 秒的判断。

> 核验还挖出一类机器原理上发现不了的东西：**共享段之后还有「本片专属广告卡」**。
> 这类卡只在这一支推广片里出现过，跨片共享数恒为 1，
> 无论是共享检测还是组内检测都看不见它（§4）。
> 实测 40 支单样本变体里有 **8 支**是这种情况，
> 最后给它们单独建了 8 支「独有」模板（tpl-0059 ~ tpl-0066）。

### 模板之间的前缀重叠能正确处理

- **整条匹配上优先** —— 学自 CAWD-660 的 204 秒模板能连上 204 帧，
  11 秒的模板只能连上 11 帧 → 选 204 秒的（切对）
- **长度相同时选更"完整"的那个** —— CAWD-660CX 只有 11 秒广告，

  204 秒模板只有 11/204=0.05 → 选 11 秒的（也切对）

两个方向都正确，不需要额外的规则。

### 踩到的十四个真实的坑

1. **`._xxx.mp4` 资源叉垃圾**
   exFAT 上 macOS 给每个文件留了 `._` 前缀的副本，**扩展名还是 .mp4**。
   第一版扫描器把它们当成了视频。现在按 `._` 前缀排除。
   （当前库里的 280 支 = 276 支 `.mp4` + 4 支 `.mpg`。）

2. **纯色画面的 dHash 恒为 0**
   dHash 只比较相邻像素，纯红卡和纯蓝卡的哈希完全一样。
   补上平均亮度分量（差 ≤ 12 才算同一画面）才堵住这个洞。
   这是写单元测试时被测出来的 —— 单元测试用纯色帧当「不同内容」，
   结果两边哈希相同，测试直接红了。

3. **聚类的代表列表和分组列表下标错位**
   `clusters` 里先塞了 REVIEW 的组，`representatives` 只记 NONE 组的代表，
   两份列表对不上 → 29 个毫无关系的视频被凑成了一组（clu-003）。
   修法是让两份列表一一对应，并补了回归测试。

4. **指纹缓存没有版本号**
   加了亮度分量之后，旧缓存里没有这一项，于是**整轮扫描的亮度校验
   被静默跳过**。现在缓存带版本号，格式一变就整体失效重算。

5. **缓存把亮度分量整个丢了**
   版本号加上了，但 `store()` 只写 hashes/mad、`load()` 也只读这两个 ——
   **brightness 拼不回来就是空列表**，`match()` 里的亮度校验被整体关掉，
   而且**没有任何报错**。最终那轮全库检测（缓存命中，3 分半跑完）
   一次亮度校验都没生效。修法：缓存里也存亮度，`CACHE_VERSION` 升到 3。

6. **裁剪点漏掉了匹配偏移**
   裁剪点直接取「模板长度」，忘了加上 `match()` 找出来的 `offset` ——
   广告从第 2 秒开始时，裁剪点会早 2 秒，广告尾巴留在片头。

7. **匹配不完整却越过了自动裁剪线**
   `0.45 + 0.5×比例` 给出 105/160 = 0.78，叠上硬切的 +0.03 正好 0.81，
   越过 0.80 → 自动裁。而那批视频的广告实际比模板短，
   切下去最多削掉 55 秒正片。分数公式区分不了「广告更短」和「广告更长」，
   只能对「匹配不完整」单独封顶。

8. **模板边界定早了 40~70 秒**
   划边界用的全景拼图只覆盖 0~180 秒，而站方推广片有 186~235 秒 ——
   量到的不是广告末尾，是「拼图恰好截断的地方」。
   8 支模板全部偏早，裁完广告还剩一大半。
   修法：观察窗口拉到 300 秒逐支重核（§2.3）。

9. **小格拼图读图会串行**
   5×4 / 5×2 的小格拼图（每格 256px）看起来够用，实际读图时
   **极易把「第几格」认错** —— `MHAR-10C`、`DVMM-070`、`SSIS-518C`、
   `SDDE-553` 等支的边界因此误判了 1~2 秒，而且**看起来完全合理**，
   肉眼根本发现不了。
   修法：改成 **512px 单格 + 3 列条带 + 每格标注「时间/平均亮度/MAD」**。
   数值（来自指纹缓存）比目测可靠 —— 亮度骤降说明进黑场、
   MAD 骤增说明画面硬切，两者互相印证，误差归零（§8.2）。

10. **`learn` 会把新模板「吃掉」**
    库里已有一条前缀相同、长度只差 ≤ 2 帧的模板时，
    `learn` 会**合并**进去而不是新建 —— 想单独建模板，结果什么都没发生。
    修法：两步走。先用明显偏短的 `--end 100` 新建一条占位，
    再用 `--replace` 改到真值。占位长度差得够远，就不会触发合并。

11. **「人工确认」优先级会把切点压短**
    模板选择把「人工确认过的模板」排在「匹配得长」前面（§3.3），
    于是一条 147 秒的**已确认**模板会赢过 230 秒的候选模板，
    哪怕后者匹配得更长 —— 那支视频的切点被压短 83 秒。
    这不是 bug，是「边界只信人工标注的模板长度」这条铁律的必然结果。
    修法：给这类视频**单独建一条属于它自己的模板**，
    让它在自己的长度上整条匹配上，拿第一档优先级。
    实测这一轮因此多建了 9 条模板、修正了 14 支视频的切点。

12. **共享段之后可能还跟着「本片专属广告卡」**
    这类卡只在这一支推广片里出现过，**跨片共享数恒为 1**，
    共享检测和组内检测原理上都看不见它（§4）。
    实测 40 支单样本变体里有 8 支是这种情况，
    机器给的边界普遍偏短 20~30 秒。
    修法：只能逐支人眼核验（§8.2），核完给它们单独建「独有」模板。

13. **`fps=1` 滤镜流水线抽出来的帧和时间对不上**
    `-ss X -t N -vf fps=1` 是最顺手的抽帧写法，但这批文件
    `start_time = 0.023023`、关键帧稀疏（有的 10 秒一个），
    **输出流的时间轴是重新起算的**。
    实测同一句 `-ss 154`，在 `SSIS-518C` 取到的是 140 多秒的内容，
    偏差可达 10 秒。
    偏差逐文件不同，所以**它不自暴露** —— 每支错的方向和幅度都不一样，
    拼图看上去永远合情合理。用它核了 182 支，**40 支切点是错的**。
    修法：逐帧精确抽帧 `ffmpeg -ss T -i F -frames:v 1`（§4.6）。

14. **模板长度改 1 帧，整族成员可能全部掉出满格**
    模板指纹是逐帧 dHash，**最后一帧恰好是广告的过渡帧**，
    这帧在不同文件里编码得不一样，dHash 就不稳定。
    把模板从 N 帧改成 N+1 帧，某些成员就从「整条匹配」掉到 N/N-1，
    判定从 CUT 退回 REVIEW。
    修法：改长度后**必须重抽指纹并逐个成员复验**；
    改不了的模板保持原样，成员长度不一致的一律进边界表。
    本轮因此退回了 7 条模板的长度修正。

## 10. 已知限制

1. **裁剪点完全依赖人工标注的模板长度。** 同一档节目换了新片头时，
   会变成 REVIEW 档，需要再 learn 一次（不会误裁）。
2. **同一族里的「变体广告」需要各自建模板。** 实测 `AV-174` 与 `ABF-094`
   属于族A，但只连续匹配上 30 帧（`AV-174` 的推广片被重新剪过一版），
   因此落到 REVIEW 档而不是自动裁。
   同理，**同一条推广片的「调色版」也要单独建模板** ——
   `JJBK-063` 和 `AKID-103` 是同一支推广片，但 105 帧之后调色不同，
   帧指纹对不上，必须分成两条模板。
3. **外挂字幕不自动偏移**（见 6.3）。
4. **广告在片头之外（片中插播）不处理** —— 模板匹配假设广告从第 0 帧开始。
5. **候选模板的机器边界并不可信，升级前必须核验。**
   2026-11-09 实测：71 支进人工确认档的视频里，**36 支的模板长度是错的**
   （最多差 53 秒）。其中 9 条模板的长度**正好等于 `scan` 的 300 秒窗口上限** ——
   那不是广告长度，是观察窗口的长度（§4.6）。
   处置方式：逐支核验后写进 `rules/ad_boundaries.yaml`，
   并把成员长度一致的候选模板升格为 `confirmed`。
   **本轮已全部核完**：边界表 71 条，可自动裁 182 支，核验相符 182 / 不符 0。
   剩下 22 条候选模板的成员长度不一致，**故意保持 candidate**，
   切点由边界表兜底 —— 它们不会单独把新片子放自动裁。

   > 注意：**候选模板本身不是安全风险，风险在「拿机器边界当真值」。**
   > 候选模板命中会落到 REVIEW 档（不会自动开刀），
   > 而边界表里写错的真值会直接被裁 —— 所以边界表只写逐帧核过的文件。

6. **边界表是「逐文件」的，新增片子不会自动获得正确切点。**
   模板能覆盖同族的新片子，边界表不能 —— 它只对写进去的那支文件生效。
   新片子命中同一条模板时，切点仍由模板长度给出（可能偏早）。
   缓解办法：把该族的代表文件核一遍，边界表记下真实值，
   其余同族文件通常只差几秒。
7. 模板库是 YAML，条目多到几千条时加载会变慢；届时可换 SQLite（接口已隔离在
   `templates.py`）。
8. **`VRNC-016.mp4` 文件损坏**（292 秒后花屏），切点核不了，
   需要重新下载。当前是全库唯一的 REVIEW 档文件。
