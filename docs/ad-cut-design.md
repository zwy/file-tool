# 片头广告识别与裁剪：方案设计

> 状态：原型已跑通（`file-tool ad-cut`），本文记录的是**实测驱动的设计**，
> 不是设想。文中所有数字都来自 `/Volumes/P7000Z/R` 真实库（276 个视频）的测量。

## 1. 要解决的问题

视频开头插了一段广告，要把它切掉。目标是：

- **尽量不靠人工** —— 人工量正比于「广告种类数」，而不是「视频数」
- **越用越快** —— 见过的广告存成模板，新视频直接对模板库检索
- **不能弄坏原片** —— 磁盘只剩 168 GiB 而素材有几百 GB，失败必须可回滚

## 2. 三个决定方案走向的实测结论

### 2.1 片头广告是**共享素材**，不是每个视频各不相同

对全库 40 个视频做前 90 秒场景切换检测，发现这样一组时间戳：

```
26.716383, 26.74975, 30.276026, 32.044461, 33.345762, 33.712796
```

它同时出现在 `ABF-094`、`ACHJ-038`、`AIAV-003`、`AV-174`、`BBAN-433`、
`CAWD-660`、`DLDSS-313`、`DVMM-104`、`DVMM-072` 等**十几个毫不相关的作品**里，
**毫秒级一致**。

另有几个规模稍小的族：

| 族 | 公共切换点 | 成员数 |
|---|---|---|
| A | `26.716383, 26.74975, 30.276026, …` | 15+ |
| B | `1.157491, 2.458792, 2.825826, …` | 4 |
| C | `1.791458, 3.092759, 3.459793, …` | 3 |
| D | `0.0897564, 0.123123, 0.189857, …` | 3 |
| E | `1.491158, 47.427845, 74.121205, …` | 2 |
| F | `1.190858, 2.492159, 2.859193, …` | 2 |

**结论：识别不是机器学习问题，是指纹检索问题。** 广告种类数远小于视频数，
人工只需要为「种类」付出代价。

### 2.2 同一支广告在不同视频里被**重新编码**过 —— 精确哈希不可用

逐像素 md5 比对：

| 对比 | 逐像素 md5 相同帧 | 结论 |
|---|---|---|
| 族B `CLT-013C` vs `DVDMS-930` | 27 / 40（前 27 秒完全一致，之后分叉） | 同一素材 |
| 族A `ABF-094` vs `ACHJ-038` | 1 / 40（**第一帧就不同**） | 同一素材，被重新编码 |
| 族D `DCV-249` vs `DVMM-012` | 0 / 40 | 同一素材，被重新编码 |

同一支广告在族A 里连**逐像素**都对不上。所以匹配必须容忍重新编码。

改用感知哈希（dHash，64 位，汉明容差 6）后：

| 对比 | 覆盖率 | 连续匹配前缀 |
|---|---|---|
| 族A 内部 | 1.00 | 45 s |
| 族B 内部 | 0.60 | 27 s |
| 族D 内部 | 0.67 | 30 s |
| **跨族（全部 30 组）** | **0.00** | **0** |

**完全可分，没有任何交叉。** dHash 是整个方案的地基。

### 2.3 广告长度跨度极大，而且**片头内部就有多个硬切**

- 最短：`CAWD-660CX` 的黑底字幕卡，**10.8 秒**
- 最长：族A 的站方推广片，**约 137 秒**（多镜头：码卡 → 电竞赞助 → 直播平台推广）
- 有的视频前 90 秒**零场景切换**（`DNW-102A`、`DNW-106B`、`ORECO-640CX`）——
  纯场景检测会直接漏判

族A 的片头内部有五六个硬切：`26.7s / 30.3s / 33.7s / 57.4s / 104.8s / …`

**这一条推翻了「用画面突变点找边界」的思路。** 任何「找最大突变」「找第一个突变」
的启发式，在族A 上都会切在广告**中间**。所以：

> **边界只信人划出来的模板长度。** 帧间差异曲线只用来**佐证**，不参与定边界。

### 2.4 关键帧结构：多数情况下可以无损流拷贝

片头区关键帧间隔（实测）：

| 文件 | 关键帧间隔 |
|---|---|
| `ABF-094` | 8.34 s |
| `CAWD-660CX` | 8.34 s（且 **10.81 s 正好是关键帧**） |
| `MBM-256` | 2.0 s |
| `ORECO-640CX` | 8.34 s |

好消息：**广告→正片的切换点经常正好是关键帧**（`CAWD-660CX` 的 10.81 秒既是画面硬切也是关键帧）。
这让「流拷贝」这个无损、几秒钟出结果的路径成为默认选择。

## 3. 系统架构

```
                     ┌─────────────┐
                     │  模板库 YAML │  rules/ad_templates.yaml
                     │  已知广告指纹 │  + 负样本
                     └──────┬──────┘
                            │ 比对
   视频 ──▶ ffprobe ──▶ 取片头指纹 ──▶ 判定 ──▶ CUT / REVIEW / NONE
              │            │           │
              │            │           └──▶ 未知族聚类（提示人工划一刀）
              │            │
              │            └──▶ 指纹缓存（重复扫描≈0 成本）
              │
              └──▶ 关键帧定位 ──▶ 流拷贝 / 重编码 ──▶ 临时文件 ──▶ 校验 ──▶ 原子替换
```

三个模块，各自职责单一：

| 模块 | 文件 | 职责 |
|---|---|---|
| 指纹层 | `file_tool/adcut/fingerprint.py` | 帧 → 64 位哈希 + 平均亮度 + 帧间差异 |
| 模板层 | `file_tool/adcut/templates.py` | 模板库的读写、学习、合并、负样本 |
| 决策层 | `file_tool/adcut/detect.py` `cut.py` | 判定、聚类、裁剪执行 |

外加两个支撑模块：`ffmpeg.py`（ffmpeg/ffprobe 调用封装）、`cache.py`（指纹缓存）。

## 4. 算法细节

### 4.1 指纹

每次取片头 180 秒的帧，缩到 32×32 灰度，对每帧算三个量：

| 量 | 作用 |
|---|---|
| **dHash（64 位）** | 主证据。相邻像素大小关系，对重新编码/缩放稳健 |
| **平均亮度（0~255）** | 补 dHash 的洞：纯色画面的 dHash 恒为 0，「纯红卡」和「纯蓝卡」在哈希上完全一样。亮度差容忍 12 |
| **帧间差异 MAD** | 佐证。裁剪点处有硬切 → 模板记对了；没有 → 模板可能记错，降档 |

两帧「算同一画面」的条件：**dHash 汉明距离 ≤ 6 且 平均亮度差 ≤ 12**。

### 4.2 匹配

模板假设出现在视频开头，允许 0~3 帧错位（有些片头前面挂着半秒黑场）。

- `prefix_len`：从起点开始**连续**匹配上的帧数
- `coverage`：整条模板被命中的比例（允许中间断开）

### 4.3 置信度

```
整条模板全匹配上 (prefix ≥ len)      → 0.95
只匹配上一部分 (prefix < len)         → 0.45 + 0.5 × (prefix / len)
裁剪点处画面差异 ≥ 12（有硬切）       → +0.03
裁剪点处画面差异 < 4（无硬切）        → −0.12
模板不是人工确认的（机器学来的）      → 封顶 0.79
```

分档：`≥ 0.80` → 自动裁；`0.55 ~ 0.80` → 待人工确认；`< 0.55` → 没有广告。

「机器学来的模板封顶 0.79」这一条是**积累机制**的核心：
机器认出来的第一回只会让自己升级，**不会**让别的视频自动开刀；
被人确认过（或第二次被机器认出）之后才升格。

### 4.4 未知族聚类

没命中任何模板的视频，按片头前 8 秒的指纹做聚类（近似匹配，不是精确相等）。

```
file-tool ad-cut cluster /Volumes/P7000Z/R
```

输出「这几组视频共享同一段还没认识的片头」，并指出每组的代表。
人工只要给**一个**代表划一刀，整组就都能自动处理了。

## 5. 人工介入模型

这是整个设计里最要紧的一环。人工量正比于**广告种类数**：

```
第 1 次：库是空的，cluster 列出所有未知片头族
         人工给每族挑一个代表，量出广告结束时间 → learn
         → 这一族的全部视频立刻变成「可自动裁」

第 2 次：新库带来的新视频里，绝大多数自动命中
         只有**新出现的广告创意**才需要再划一刀

第 N 次：人工介入次数 ≈ 期间新增的广告种类数（很少）
```

`learn` 会自动判断「这支广告是不是已经有了」：
连续匹配 ≥ 85% 且长度差 ≤ 2 帧 → 合并进已有模板（`samples` 递增）；
否则新建一条。

**长度差超过 2 帧就分开建模板**，因为同一档节目换了新片头时，
前 3 秒一样、后面不一样 —— 混在一起会把模板拉长，
匹配时连续段提前断掉，裁剪点会落到广告中间。

### 负样本

`ad-cut reject VIDEO --end 12 --reason "这里没有广告"` 记一条负样本。
作用是抑制误切：片头本来就是静止画面时（黑场、站点 logo 动画），
dHash 有可能撞上某个模板；负样本让这类误报在下一轮被挡下来。

## 6. 裁剪执行语义

### 6.1 原地替换，绝不另存

磁盘只剩 168 GiB，素材几百 GB —— 另存一份再删是不可能的。
但直接「输出新文件 → 删原片」，中途失败就两头都没了。

所以顺序固定：

1. 裁到**同目录下的临时文件** `xxx.adcut-tmp.mp4`（同卷 → rename 原子）
2. 校验：文件大小、视频轨在、音频轨在（原片有的话）、时长 ≈ 原时长 − 裁剪点
   （容差 2.5 秒 + 原片 1%）
3. 校验通过才 `os.replace()` 顶掉原片（并保留原权限）

**任何一步失败：临时文件删掉，原片原封不动。**

### 6.2 流拷贝 vs 重编码

耗时差一个数量级：流拷贝一个 10 GB 的片子几秒钟，重编码几十分钟。

选择规则：

1. 切割点**之后**最近的关键帧，距离 ≤ `--max-snap`（默认 2 秒）→ 流拷贝
   （广告切得干干净净）
2. 否则看切割点**之前**最近的关键帧，距离 ≤ `--max-snap` → 流拷贝
   （会留一截广告尾巴，但快几十倍）
3. 都不满足 → 重编码，切在精确帧上（`--accurate` 可强制）

实测 `CAWD-660CX`：模板裁剪点 11.0 秒 → 吸附到关键帧 10.81 秒
（偏移 −0.19 秒）→ 流拷贝，1.6 GB 的片子几秒完成，
结果时长 7096.306 秒（期望 7096.307），首帧已是正片。

### 6.3 字幕

R 库实测**没有外挂字幕**（只有封面 jpg），所以当前不自动偏移时间轴。

但检测到同名外挂字幕时会**告警**：视频前 N 秒被切掉，
字幕还按原来的时间轴走，内容会整体错位。
接口已预留（`detect._subtitle_note`），后续补偏移模块即可。

## 7. 性能

| 操作 | 耗时 |
|---|---|
| 取片头 180 秒指纹（1080p） | 1.5 ~ 7 s / 视频 |
| 关键帧探测（前 180 秒） | ~1.1 s / 视频 |
| 模板匹配（几十条模板 × 180 帧） | < 10 ms |
| **重复扫描（命中指纹缓存）** | **0.58 s / 8 个视频** |

缓存键包含**文件大小和修改时间** —— 文件被换掉后指纹自动失效重算。
缓存按平台惯例放在 `~/Library/Caches/file-tool/adcut`（Windows: `%LOCALAPPDATA%`）。

「越来越快」有两个含义，都实现了：

1. **人工越来越少** —— 模板库越全，需要划的刀越少
2. **机器越来越快** —— 指纹缓存命中后重复扫描几乎零成本

## 8. 实战验证结果

在 `/Volumes/P7000Z/R`（**280 个视频**，2~4 小时/个，总计数百 GB）上实测。

### 只学 2 支广告模板的结果

```bash
file-tool ad-cut learn .../CAWD-660CX.mp4 --end 10.9  --label "厂牌片头-黑底字幕卡"
file-tool ad-cut learn .../ABF-094.mp4   --end 137   --label "站方推广片"
```

| 判定 | 数量 | 说明 |
|---|---|---|
| **可自动裁** | **41** | 置信 0.90~0.98，裁剪点 11s 或 137s |
| **待确认** | **47** | 匹配上但只对上一部分（片头的**变体**） |
| 无广告 | 184 | 其中 1 个开头 94% 静止，被单独标出 |
| 跳过 | 8 | 文件损坏（无 moov atom）或 0 字节 |

**41 个视频的人工介入是零** —— 两刀换来 41 个自动。

### 剩下的人工量：14 刀

`ad-cut cluster` 在全库找到 **14 组共享片头，覆盖 145 个视频**：

| 组 | 成员数 | 说明 |
|---|---|---|
| clu-001 | 42 | 族A 推广片的变体（前 30 帧相同，之后分叉） |
| clu-002 | 5 | 族A 推广片的另一个变体（前 57 帧相同） |
| clu-003 | 29 | 完全未知的片头族 |
| clu-004 | 25 | 另一支未知片头族 |
| … | | 共 14 组 |

分叉点 30 帧和 57 帧正好落在推广片**内部的镜头切换**上
（26.7s / 30.3s / 33.7s / 57.4s）—— 这不是巧合，正是「同一支推广片的
不同剪辑版本」的证据。

**再划 14 刀，这 145 个视频就全部自动化了。**
人工总量：2 + 14 = **16 刀 / 280 个视频**。

### 速度

| 场景 | 耗时 |
|---|---|
| 首次全库扫描（冷缓存，6 并发） | 约 25 分钟 |
| **缓存命中后全库重扫** | **12~13 秒** |

缓存键含文件大小和修改时间，换片自动失效重算。

### 一次真实的裁剪

```
$ file-tool ad-cut cut /Volumes/P7000Z/.adcut_test --apply
  ✓ CAWD-660CX.mp4  已裁掉 10.81s（copy），吸附偏移 -0.19s

裁剪完成：成功 1 个，失败 0 个（失败的原片保持不变）。
```

- 1.6 GB 的片子，几秒完成（流拷贝，无损）
- 时长 7096.306 秒（期望 7096.307，误差 0.001 秒）
- 首帧已是正片（原来是被切掉的黑底字幕卡）
- 权限保留（`-rwx------`），无临时文件残留

### 踩到的两个真实的坑

1. **`._xxx.mp4` 资源叉垃圾**
   exFAT 上 macOS 给每个文件留了 `._` 前缀的副本，**扩展名还是 .mp4**。
   第一版扫描器把它们当成了视频（280 vs 276）。现在按 `._` 前缀排除。

2. **纯色画面的 dHash 恒为 0**
   dHash 只比较相邻像素，纯红卡和纯蓝卡的哈希完全一样。
   补上平均亮度分量（差 ≤ 12 才算同一画面）才堵住这个洞。
   这是写测试时被测出来的 —— 单元测试用纯色帧当「不同内容」，
   结果两边哈希相同，测试直接红了。

## 9. 命令

```bash
# 扫描：判断每个视频开头有没有广告
file-tool ad-cut scan /Volumes/P7000Z/R

# 聚类：找出还没认识的片头，按相似度分组
file-tool ad-cut cluster /Volumes/P7000Z/R

# 学习：给一支广告划一刀（同族全部自动命中）
file-tool ad-cut learn /Volumes/P7000Z/R/CAWD-660CX/CAWD-660CX.mp4 --end 10.9 --label "厂牌片头"

# 否定：这里其实没有广告，别再切
file-tool ad-cut reject <video> --end 12 --reason "正片"

# 时间轴拼图：肉眼确认广告在哪结束（没装 drawtext，时间按格数推算）
file-tool ad-cut sheet /Volumes/P7000Z/R/ABF-094/ABF-094.mp4 --at 137

# 裁剪：默认只预览，--apply 才动手
file-tool ad-cut cut /Volumes/P7000Z/R --apply

# 模板库 / 指纹缓存
file-tool ad-cut templates
file-tool ad-cut cache --clear
```

所有写操作都是**先预览后执行**，和本仓库其它命令一致。

## 10. 已知限制

1. **裁剪点完全依赖人工标注的模板长度。** 同一档节目换了新片头时，
   会变成 REVIEW 档，需要再 learn 一次（不会误裁）。
2. **同一族里的「变体广告」需要各自建模板。** 实测 `AV-174` 与 `ABF-094`
   属于族A，但只连续匹配上 30 帧（`AV-174` 的推广片被重新剪过一版），
   因此落到 REVIEW 档而不是自动裁。
3. **外挂字幕不自动偏移**（见 6.3）。
4. **广告在片头之外（片中插播）不处理** —— 模板匹配假设广告从第 0 帧开始。
5. 模板库是 YAML，条目多到几千条时加载会变慢；届时可换 SQLite（接口已隔离在
   `templates.py`）。

裁完广告后，视频名通常还是下载站的原样（`aavv38.xyz@DVDMS-977.mp4`），
和裁剪串成一条流水线正合适。
