# file-tool

本地文件整理 CLI。面向「番号」形态的媒体库：把杂乱的目录结构整理成
「一个作品一个目录」，并处理重复副本、系统垃圾、误放内容。

> 本工具只操作**文件名和目录结构**，不读取、不解析、不修改媒体内容。

## 功能

- **tidy** —— 智能整理一个目录：自动识别形态、编排动作、统一预览（**推荐入口**）
- **isolate** —— 把**不符合番号规范的目录**挪到别处（如非番号内容挪去 `/Volumes/P7000Z/GC`）
- **clean** —— 递归清理 macOS 资源叉垃圾（`._xxx` / `.DS_Store`）
- **rename** —— 按番号规则批量规范化**子目录名**（去水印域名、去重复副本标记、统一「厂牌-数字」格式与**大写**）
- **rename-files** —— 规范化**文件名里带的番号**（目录名已规范，文件还留着下载原样）
- **merge** —— 把**同名目录**合并成一个（按**文件内容指纹**判定重复，按**体积**分配撞名）
- **archive** —— 把**平铺在一个目录里的文件**按归一番号分装进子目录
- **ad-cut** —— 识别并裁掉视频**开头插的广告**（模板库积累，人工量正比于广告种类数）

## 设计原则

**一切默认 dry-run。** 所有命令不加 `--apply` 只输出计划，不动文件。

**判定看内容，不看名字。** 目录名带 `(1)` 不代表是复制副本 —— 也可能是同作品的不同画质版本
或分 P。只看名字就合并会直接销毁数据，所以重复判定用**文件内容指纹**。

**规则与代码分离。** 番号形态定义在 `rules/numbering.yaml`，改规则不用改代码。

**规范名只有一种写法。** 统一大写（`uppercase: true`）—— 整理出来的库最终要放到
exFAT 上，那边大小写不敏感，两个只差大小写的名字会撞车。

**不认识就不动。** 无法识别的目录原样保留并报告，绝不猜测。

## 环境

需要 Python 3.11+。

```bash
# macOS / Linux
cd /path/to/file-tool
python3 -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"
```

```powershell
# Windows
cd D:\path\to\file-tool
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -e ".[dev]"
```

依赖：`typer`（CLI）、`pydantic`（规则校验）、`PyYAML`（规则文件）。开发依赖 `pytest`。

### 装成全局命令

两个脚本都做同一件事：生成一个指向仓库内 `.venv` 的 launcher，
**仓库改了不用重装**。

```bash
./scripts/install_cli.sh                      # macOS / Linux -> ~/.local/bin/file-tool
./scripts/install_cli.sh --add-to-path        # 并写进 PATH
```

```powershell
# Windows -> %LOCALAPPDATA%\file-tool\bin\file-tool.cmd
powershell -ExecutionPolicy Bypass -File scripts\install_cli.ps1
powershell -ExecutionPolicy Bypass -File scripts\install_cli.ps1 -AddToPath
```

> Windows 上 `.ps1` 必须存成 **UTF-8 with BOM**。PowerShell 5.1 没有 BOM 就按
> ANSI 代码页读，脚本里的中文会把语法搞乱（报「意外的标记」）。VS Code 右下角
> 选 `UTF-8 with BOM` 即可。

## 命令

```bash
# 路径按自己的平台换：macOS /Volumes/P7000Z/R，Windows D:\Media\R
file-tool tidy    /Volumes/P7000Z/R      # 智能整理（自动判断该做什么）
file-tool tidy    /Volumes/P7000Z/R --apply

file-tool isolate /Volumes/P7000Z/R --to /Volumes/P7000Z/GC            # 隔离不符合规范的目录
file-tool isolate /Volumes/P7000Z/R --to /Volumes/P7000Z/GC --apply

file-tool scan   /Volumes/P7000Z/R            # 只统计，不改动
file-tool rename /Volumes/P7000Z/R            # 预览改名计划（默认 dry-run）
file-tool rename /Volumes/P7000Z/R --apply    # 真正执行改名
file-tool rename-files /Volumes/P7000Z/R        # 预览文件名番号规范化
file-tool rename-files /Volumes/P7000Z/R --apply
file-tool merge  /Volumes/P7000Z/R            # 预览合并计划（含内容比对结论）
file-tool merge  /Volumes/P7000Z/R --apply    # 真正执行合并
file-tool archive /Volumes/P7000Z/CLUB        # 预览分装计划
file-tool archive /Volumes/P7000Z/CLUB --apply  # 真正执行分装
file-tool clean   /Volumes/P7000Z/IMG         # 递归清理资源叉垃圾
file-tool clean   /Volumes/P7000Z/IMG --apply
file-tool rules  show                         # 查看当前规则集

# 裁掉片头广告（详见下面「ad-cut」一节）
file-tool ad-cut scan     /Volumes/P7000Z/R          # 判断每个视频开头有没有广告
file-tool ad-cut cluster  /Volumes/P7000Z/R          # 找出还没认识的片头，按相似度分组
file-tool ad-cut learn    <video> --end 10.9         # 给一支广告划一刀（同族全部自动命中）
file-tool ad-cut cut      /Volumes/P7000Z/R --apply  # 真正裁掉（默认只预览）
file-tool ad-cut templates                         # 查看模板库
```

Windows 上路径带盘符，含空格要加引号：

```powershell
file-tool tidy "D:\Media\R"
file-tool isolate "D:\Media\R" --to "D:\Media\GC"
```

所有命令默认只预览，加 `--apply` 才落盘。加 `--json` 输出机器可读的计划
（stdout 上**只有** JSON，可以直接喂给 `jq` 或 `json.loads`）。

未安装时可用模块方式运行：`python -m file_tool.cli <命令>`。

> PowerShell 的 `>` 重定向会写 UTF-8 **带 BOM**，下游 `json.loads` 会报
> `Unexpected UTF-8 BOM`。要纯 JSON 就用 `| Out-File -Encoding utf8NoBOM`，
> 或者直接让 Python 读管道。工具本身输出的字节是干净的 UTF-8，无 BOM。

## 平台差异（Windows / macOS）

工具在两个平台上都能跑，但文件系统规则不同 —— 差异都收在
`file_tool/fscompat.py` 一处，下面是用户能看到的差异。

### 文件名规则

Windows 有一批 macOS 不允许的名字：**保留设备名**（`CON` `NUL` `COM1`，
带扩展名也一样）、**非法字符**（`< > : " / \ | ? *`）、**结尾的点和空格**
（会被静默剥掉）。

exFAT 卷在 macOS 上能建出带 `:` 的文件名，插到 Windows 上就成了碰不了的
僵尸文件 —— 连 `stat` 都会失败。工具在扫描时会识别这类名字：

- **Windows 上**：不碰它，如实报告（`archive` / `isolate` / `rename-files`
  的计划里会单列出来）
- **macOS 上**：名字完全合法，照常处理（`rename-files` 反而能顺手把它改好）

两边的**报告措辞也跟着平台走**，这是硬要求 —— 措辞必须和磁盘实际状态对得上：

| 平台 | 报告说的是 | 实际发生了什么 |
| --- | --- | --- |
| Windows | 「Windows 上无法访问，已跳过」 | 确实跳过了 |
| macOS | 「在 Windows 上无法访问（本平台已照常处理）」 | **照常处理了** |

早期版本两边共用一句「已原地保留」，于是 macOS 上目录明明被挪走了，
输出却说它留在原地 —— 用户照这句话判断「哪些文件能安全带去 Windows」，
结论正好反过来。这条不变量由 `tests/test_platform_parity.py` 钉死。

另外，`isolate` 的这份清单里**只会有目录**，`archive` 的**只会有文件** ——
平铺文件从来不是隔离候选，目录也不参与分装，不该混进对方的报告里。

### 大小写

Windows NTFS/exFAT 与 macOS APFS（默认）都**大小写不敏感**。仅大小写不同的
改名走两步（先挪临时名再改目标名），否则 rename 会「无事发生」。

但 Linux ext4、macOS 的**大小写敏感**分区是相反的 —— 那里 `a.mp4` 和
`A.mp4` 是两个不同的文件。工具不能把「目标名是否已被占用」这个问题交给
文件系统去回答，理由见下面「冲突判定与卷的大小写语义无关」。

### 文件占用

macOS 允许删改正在打开的文件，Windows 不允许。资源管理器预览窗、播放器、
杀毒软件都可能占着文件。工具的做法是**跳过这个文件、记成失败、继续处理下一个**，
而不是让整次操作抛异常中断，留下「并了一半」的目录。

```powershell
file-tool merge D:\Media\R --apply
# ...
#   共 3 个文件未能并入 —— 通常是被其他程序占用（资源管理器预览窗、播放器）。
#   关掉占用者后重跑即可。
```

### 控制台编码

Windows 控制台默认代码页是 GBK / cp437 / cp1252，中文输出会直接
`UnicodeEncodeError` 崩掉整个 CLI。工具启动时会把 stdout/stderr 切到 UTF-8，
所以在任何代码页下都能正常输出中文。

**「无法表示的字符降级成 `?`」这一步只在 Windows 上做。** POSIX
（macOS / Linux）默认就是 UTF-8，那里的编码错误是真实问题（文件名里有
无法表示的字节），静默替换成 `?` 只会把问题藏起来 —— 用户看到的是一个
合法的文件名，磁盘上却是另一串字节。POSIX 上保持严格策略，让它报出来。

### 路径分隔符

JSON 输出和 CLI 里的**相对路径统一用 `/`**（`ACHJ-038/子目录/x.mp4`），
不随平台变。下游脚本可以跨平台复用。

### 长度限制

Windows 的 `MAX_PATH` 是 260 字符。Python 本身是长路径感知的，能绕过，
但资源管理器和很多播放器不行。深层目录（番号目录往下 3~5 层）配长中文名时
要注意。

## clean：递归清理资源叉垃圾

macOS 在 exFAT 等非 HFS+ 卷上，为每个文件建一个 `._xxx` 资源叉副本。
Windows 在同样的卷上会留 `Thumbs.db`。媒体文件不需要这些元数据，它们是纯粹的垃圾。

实测 `/Volumes/P7000Z/IMG` 嵌套层有 **24000 多个**，`R` 有 7000 多个。

```bash
file-tool clean /Volumes/P7000Z/IMG            # 预览
file-tool clean /Volumes/P7000Z/IMG --apply    # 执行
```

只删资源叉，**真实文件和目录一律不动**。

## isolate：把不符合规范的目录挪走

番号库里混进了不该在的目录 —— 非番号内容、散装合集、随手下载的杂项。
`isolate` 把它们挪到另一个目录，让番号库只留番号。

```bash
file-tool isolate /Volumes/P7000Z/R --to /Volumes/P7000Z/GC
file-tool isolate /Volumes/P7000Z/R --to /Volumes/P7000Z/GC --apply
```

也可以并进 tidy：`file-tool tidy /Volumes/P7000Z/R --isolate /Volumes/P7000Z/GC --apply`

### 判定看内容，不看目录名

只看名字会误判。实测 `/Volumes/P7000Z/R` 的 17 个未匹配目录：

| 目录 | 名字像番号？ | 实际内容 | 判定 |
|---|---|---|---|
| `02` `03` `10` `31` | 否 | 非番号，文件名 `mp4_ (1).mp4` | **挪走** |
| `05` `09` `11` | 否 | 非番号，中文标题 | **挪走** |
| `175_中文标题片段...` | 否 | 非番号，中文标题 | **挪走** |
| `414-中文标题片段...` | 否 | 非番号，中文标题 | **挪走** |
| `collection-cn-a` | 否 | 非番号合集，52 个中文标题子目录 | **挪走** |
| `collection-cn-b` | 否 | 非番号合集 | **挪走** |
| `collection-cn-c` | 否 | 非番号合集 | **挪走** |
| `kfa11.com@中文标题...` | 否 | 非番号 | **挪走** |
| `Uncensored Leaked_001` | 否 | **正规番号合集**：ABP-001 等 15 个 | **保留** |
| `XXX-AV系列合集` | 否 | **正规番号合集**：AV-20608 等 28 个 | **保留** |

后两个名字也不像番号，但内含**正规番号**，不该被当成杂项移走。
所以判定要下探到内容：目录内（含子目录）是否出现番号形态的文件名。

实际结果：**15 个挪走，2 个保留**。

### 安全语义

- 目标已有同名目录 → 加序号（`02` → `02 (2)`），**绝不覆盖**
- 目标目录本身不会被挪进自己
- 目标在源目录**内部** → 直接拒绝（会造成目录嵌套）
- 只处理**子目录**，平铺文件归 archive 管
- 空目录默认也挪走（`--keep-empty` 可保留）

## tidy：智能整理

一个入口搞定所有形态。**不用为每个目录手工挑命令**。

### 形态自动识别

以**顶层**为界，靠「有多少个子目录名能被番号规则识别」判定：

| 形态 | 特征 | 动作 |
|---|---|---|
| `flat` | 0 个子目录，文件平铺 | 清理 → 分装 |
| `nested` | 子目录名大多是番号 | 清理 → 合并 → 改名 |
| `mixed` | 番号目录 + 平铺文件 | 清理 → 合并 → 分装 → 改名 |
| `loose` | 有子目录但没几个像番号 | **只报告，不动** |

实测你的磁盘：

```
/Volumes/P7000Z/R      NESTED  (706/723 个子目录名可识别为番号)
/Volumes/P7000Z/CLUB   FLAT    (没有子目录，104 个平铺文件)
/Volumes/P7000Z/IMG    NESTED  (313/324 个子目录名可识别为番号)
/Volumes/P7000Z/boy    LOOSE   (0/1 个子目录名像番号)
/Volumes/P7000Z/共享   LOOSE   (0/2 个子目录名像番号)
```

`loose` 形态不动手 —— `共享` 里是 `github-recovery-codes.txt` 这类东西，
套番号规则只会破坏它。

### 动作编排顺序

```
clean → isolate → merge → archive → rename → rename-files
```

**isolate 排在最前**：先把不符合规范的目录挪走，剩下的才都是干净的番号目录。

**merge 必须排在 rename 之前**：合并后目录数减少，改名时的冲突检测更准；
反过来先改名，合并要在改名后的名字里重新识别重复标记，多一道解析。

**archive 与 rename 有先后依赖**：先把平铺文件装进目录，才谈得上给它们改名。

**rename-files 必须排在 rename 之后**：文件名的目标来自**所在目录的规范名**，
目录名先规范化，文件才有正确的目标可对。

> 早期版本 `tidy` 只改目录名，文件名里的番号要另外跑 `rename-files` ——
> 「一个命令搞定」的说法站不住。现在这一步已经并进 `tidy`。
> 不想动文件名就加 `--no-file-rename`。

### 为什么只看顶层，不递归

实测 `R` 目录的两层语义完全不同：

```
第 1 层：SDMM028C, DOW24070403        ← 番号，该规范化
第 2 层：《某中文标题》副标题...   ← 原始标题，绝不能动
```

第二层是**原始标题**，对它套番号规则只会破坏信息。所以递归只用于**内容比对**
（merge 需要看内部文件），不用于改名。

### 预览输出

```
目录：/Volumes/P7000Z/IMG
识别形态：NESTED  （313/324 个子目录名可识别为番号）
[清理] 清理系统垃圾文件（.DS_Store / ._ 资源叉） —— 2 项
     .DS_Store
     ._.DS_Store
[合并] 合并内容完全一致的重复目录 —— 1 项
     FLUP-1131720
[改名] 按番号规则规范化目录名 —— 307 项
     7K24042302
     …

提示：
  • 1 组部分重叠（内容不同），默认不合并：HEA-240609-02
  • 13 个目录名不是番号，原样保留：02, 03, 05, collection-cn-a…
```

## archive：平铺文件 → 按番号建目录

`/Volumes/P7000Z/CLUB` 是**完全平铺**的目录 —— 0 个子目录、208 个文件
（104 个真实文件 + 104 个 `._` 资源叉）。archive 把它们变成「一个番号一个目录」。

### 两种变体归一到同一目录

| 归一类型 | 例子 | 依据 |
|---|---|---|
| **横杠变体** | `CLUB810` + `CLUB-810` → `CLUB-810/` | 文件指纹证实内容不同（3.0GB vs 1.6GB），是同一番号的不同片源 |
| **C 后缀** | `CLUB830` + `CLUB830C` → `CLUB-830/` | 封面指纹完全相同（`3f0299f4750ceea9`），`C` = 中文字幕版 |

归一后 104 个文件 → **53 个番号目录**，其中 4 组由多个变体合并而来：

```
CLUB-806/  CLUB-806C.mp4, CLUB806C.jpg, CLUB806C.mp4
CLUB-810/  CLUB-810.mp4, CLUB810.jpg, CLUB810.mp4
CLUB-830/  CLUB830.jpg, CLUB830.mp4, CLUB830C.jpg, CLUB830C.mp4
CLUB-835/  CLUB835.jpg, CLUB835.mp4, CLUB835C.jpg, CLUB835C.mp4
```

### 安全语义

- **不删除任何视频文件** —— 归一是合并进同一目录，不是去重
- 目标目录已有同名文件 → **跳过并报告**，绝不覆盖
- 目录名与现有**文件**撞名 → 整组不处理，报告出来
- `._` 资源叉文件是 macOS 垃圾 → 默认清理（`--keep-forks` 可保留）
- 只处理媒体扩展名（视频、图片、**字幕**），其他文件原地保留并报告
  - 平铺文件的番号要从**剥掉水印域名**之后取：`hhd800.com@DVDMS-977.mp4`
    的目录名是 `DVDMS-977`，不是整串
- 已存在的子目录**不递归、不合并**

## ad-cut：裁掉开头插的广告

视频开头插了一段广告，要把它切掉。工具做三件事：**认出这是什么广告**、
**定出切到哪儿**、**安全地切掉**。

> 详细设计、实测数据与算法推导见 [`docs/ad-cut-design.md`](docs/ad-cut-design.md)。
> 这一节是使用层面的说明。

### 为什么能「抛开人工」

实测 `/Volumes/P7000Z/R` 的 276 个视频，片头广告**不是每个视频各不相同** ——
同一支广告素材被反复插在几十个不同番号前面。对全库做前 90 秒场景切换检测，
下面这串时间戳同时出现在 `ABF-094`、`ACHJ-038`、`AIAV-003`、`AV-174`、
`BBAN-433`、`CAWD-660` 等十几个毫不相关的作品里，**毫秒级一致**：

```
26.716383, 26.74975, 30.276026, 32.044461, 33.345762, 33.712796
```

所以「识别」不是机器学习问题，是**指纹检索**问题：
见过的广告存成模板，新视频来了先算指纹再对模板库检索。

### 同一支广告在每个视频里都被重新编码过

逐像素 md5 比对，同族的 `ABF-094` 与 `ACHJ-038` **第一帧就不同** ——
精确哈希在这里完全不可用。改用感知哈希（dHash 64 位，汉明容差 6）后：

| 对比 | 覆盖率 | 连续匹配前缀 |
|---|---|---|
| 同族之间 | 0.60 ~ 1.00 | 27 ~ 45 秒 |
| **跨族（全部 30 组）** | **0.00** | **0** |

完全可分，没有任何交叉。

### 裁剪点只信人工划的模板长度

这是最容易被做错的一处。族A 的片头是一段**约 137 秒的连续推广片**，
内部有五六个硬切（26.7s / 30.3s / 33.7s / 57.4s / 104.8s …）。

任何「找画面突变点当边界」的启发式，在族A 上都会切在广告**中间**。
所以：边界只认**人划出来的模板长度**，帧间差异曲线只用来佐证
（裁剪点处有硬切 → 模板记对了；没有 → 降档到人工确认）。

### 工作流

```bash
# 1) 先看库里有几组还没认识的片头
file-tool ad-cut cluster /Volumes/P7000Z/R
#    [clu-001] 42 个视频共享同一段片头
#      模板 tpl-0002 的变体（前 30 帧相同，之后分叉）
#    [clu-002] 5 个视频共享同一段片头
#    ...
#    发现 14 组未知片头，共覆盖 145 个视频

# 2) 给每个族挑一个代表，量出广告结束时间，学进模板库
file-tool ad-cut learn /Volumes/P7000Z/R/ABF-094/ABF-094.mp4 --end 137 --label "站方推广片"

# 3) 不确定切到哪？生成时间轴拼图，一眼看分界
file-tool ad-cut sheet /Volumes/P7000Z/R/ABF-094/ABF-094.mp4 --at 137
#    拼图：ABF-094-sheet.png
#    从 107.0s 开始，每格 3 秒，5×4 格：
#      第1格=107s  第2格=110s  第3格=113s  …

# 4) 之后这一族的视频全部自动命中
file-tool ad-cut scan /Volumes/P7000Z/R
#    共 280 个视频 | 可裁 41 | 待确认 47 | 无广告 184 | 跳过 8

# 5) 裁（默认只预览）
file-tool ad-cut cut /Volumes/P7000Z/R
file-tool ad-cut cut /Volumes/P7000Z/R --apply
```

人工量正比于**广告种类数**，不是视频数。实测：2 刀换来 41 个视频全自动，
再划 14 刀覆盖另外 145 个，**总共 16 刀 / 280 个视频**。

### 实战结果（`/Volumes/P7000Z/R`，280 个视频）

只学 2 支广告模板之后：

| 判定 | 数量 | 说明 |
|---|---|---|
| **可自动裁** | **41** | 置信 0.90~0.98 |
| 待确认 | 47 | 匹配上但只对上一部分 —— 片头的**变体** |
| 无广告 | 184 | 其中 1 个开头 94% 静止，被单独标出 |
| 跳过 | 8 | 文件损坏（无 moov atom）或 0 字节 |

`cluster` 在全库找到 **14 组共享片头，覆盖 145 个视频**。
其中两组的分叉点是 30 帧和 57 帧 —— 正好落在推广片**内部的镜头切换**上
（26.7s / 30.3s / 33.7s / 57.4s），这是「同一支推广片的不同剪辑版本」的证据。

### 裁剪怎么保证不弄坏原片

磁盘只剩 168 GiB 而素材有几百 GB，**不能另存一份再删**。
但直接「输出新文件 → 删原片」，中途失败就两头都没了。所以顺序固定：

1. 裁到**同目录下的临时文件** `xxx.adcut-tmp.mp4`（同卷 → rename 是原子的）
2. **校验**：文件大小、视频轨在、原片有音频则音频轨也要在、
   时长 ≈ 原时长 − 裁剪点（容差 2.5 秒 + 原片 1%）
3. 校验通过才 `os.replace()` 顶掉原片（保留原权限）

**任何一步失败：临时文件删掉，原片原封不动。**

### 拷贝还是重编码

耗时差一个数量级：流拷贝一个 10 GB 的片子几秒钟，重编码几十分钟。

1. 切割点**之后**最近的关键帧，距离 ≤ `--max-snap`（默认 2 秒）→ 流拷贝
2. 否则看切割点**之前**最近的关键帧，距离 ≤ `--max-snap` → 流拷贝
   （会留一截广告尾巴，但快几十倍）
3. 都不满足 → 重编码，切在精确帧上（`--accurate` 强制）

实测 `CAWD-660CX`：模板裁剪点 11.0 秒 → 吸附到关键帧 10.81 秒
（偏移 −0.19 秒）→ 流拷贝，1.6 GB 几秒完成，结果时长 7096.306 秒
（期望 7096.307），首帧已是正片，权限保留，无临时文件残留。

### 字幕

R 库实测**没有外挂字幕**（只有封面 jpg），所以当前不自动偏移时间轴。
检测到同名外挂字幕时会**告警**：视频前 N 秒被切掉，字幕还按原来的时间轴走，
内容会整体错位。接口已预留，后续补偏移模块即可。

### 性能

| 场景 | 耗时 |
|---|---|
| 取片头 180 秒指纹（1080p） | 1.5 ~ 7 s / 视频 |
| 模板匹配（几十条模板 × 180 帧） | < 10 ms |
| 首次全库扫描（280 个视频，冷缓存） | 约 25 分钟 |
| **缓存命中后全库重扫** | **12~13 秒** |

「越来越快」有两个含义，都实现了：**人工越来越少**（模板库越全，需要划的刀越少）、
**机器越来越快**（指纹缓存命中后重复扫描几乎零成本）。

### 踩到的两个坑

1. **`._xxx.mp4` 资源叉垃圾** —— exFAT 上 macOS 给每个文件留了 `._` 前缀的副本，
   **扩展名还是 .mp4**，第一版扫描器把它们当成了视频（280 vs 276）。现在按 `._` 前缀排除。
2. **纯色画面的 dHash 恒为 0** —— dHash 只比较相邻像素，纯红卡和纯蓝卡的哈希完全一样。
   补上平均亮度分量（差 ≤ 12 才算同一画面）才堵住这个洞。
   这是写单元测试时被测出来的：测试拿纯色帧当「不同内容」，结果两边哈希相同，测试直接红了。

## rename-files：文件名里的番号规范化

目录名已经规范过了，但目录里的文件还留着下载时的原样：

```
ACHJ-038/kfa11.com@ACHJ038.jpg    ->  ACHJ-038.jpg
CLT-013C/aavv39.xyz@733CLT-013C.jpg -> CLT-013C.jpg
BDSR-436/BDSR436.mp4               ->  BDSR-436.mp4
```

### 番号取自顶层目录

实测的目录结构比想象中深 —— 番号目录往下还有 2~5 层：

| 层级 | 内容 |
|---|---|
| `ACHJ-038/` | 顶层 = 番号目录 |
| `FLUP-1131784/广东财经大学 校鸡公交车.../` | 原标题子目录 |
| `TEA-240813-08/132 -SSQW/SSQWQS/图片/` | 厂牌 / 分类分组 |
| `xfxfz-14501/3505.7z/SF/1/` | 解压残留（压缩包名当目录） |

番号身份只在**顶层目录**，往下几层都不承载番号信息。

### 只处理「文件名里本来就有番号」的

文件名解析不出番号的一律不动 —— 那些名字本身就是内容标识：

- 中文标题（`一见面就湿透.mp4`）—— 标题就是身份，套番号会毁掉信息
- 图片序列（`001.jpg`）—— 序号有意义
- 原始导出名（`VID_20240713_021421_921.mp4`、`dzud43.jpg`）

判定「是不是同一个作品」用**基础名**（不含重复副本标记）比对：
文件名解析出的基础名 == 所在目录的基础名 → 规范化；不等 → 判定不动并报告
（`STSK-108/aavv38.xyz@STSK108A.mp4` 是另一个作品，不动）。

比对时忽略两件事：**大小写**和**数字段的前导零**。
下载站给同一部片子写过 `GVH067` 和 `gvh00067` —— 卷本身大小写不敏感
（Windows / macOS APFS 默认），数字位数不同但值相同，是同一部番号。
按字面比较会把它误判成「别的番号」而跳过。

### 番号后面带噪声后缀

下载站常在番号后面接一串东西，把整个文件名挡在解析之外：

| 原始文件名 | 噪声 | 结果 |
|---|---|---|
| `326FCT-043_en.srt` | 语言标记 `_en` | `FCT-043_en.srt` |
| `259LUXU-1812.mp4.jpg` | 二次扩展名 `.mp4` | `LUXU-1812.mp4.jpg` |
| `MKMP595-2f60f24e4602.mp4` | 去重哈希 | `MKMP-595-2f60f24e4602.mp4` |
| `STARS-542~nyap2p.com.mp4` | 站点名 | `STARS-542~nyap2p.com.mp4` |

做法是**逐段截断试解析**：把分隔符之后的部分当成噪声后缀，前缀能解析成
番号就用。噪声后缀**原样保留** —— 语言标记是有意义的信息，删掉就毁了。

实测一个 640 文件的库：这一项加上去之后，带水印域名的文件名从 350 个
降到 3 个（2 个是站点名残留、1 个是垃圾 `.url.txt`，都不是番号）。

### 分段标记 `-2` 不能被规则吞掉

番号后面的 `-N` 有两种含义，规则文件里对应着两条不同的剥离规则：

| 形态 | 含义 | 规则 |
|---|---|---|
| `CLUB-880 (2)` | **重复副本**（目录级） | `strip_paren_dup` |
| `SODS-068-2.mp4` | **分段 / 版本**（文件级） | 不剥 |

`strip_hyphen_dup` 规则会把尾部的 `-2` 当成重复副本标记剥掉。用于目录名没问题
（目录不会有「第 2 集」），但用在**文件名**上就会出事：H 盘 `sdjs-361/` 目录里
放着 `sdjs-361.mp4` 和 `4k2.me@sdjs-361-2.mp4`，`-2` 被剥掉后文件名变成
`sdjs-361.mp4` —— 跟已有的真身撞名，于是被判成冲突跳过，**水印永远去不掉**。

修法是**整串解析与逐段截断两路都算一遍**：两者指向同一部片子时取逐段截断的结果，
被剥掉的标记就留在后缀里（`-2`）。两者指向不同片子时取整串解析的结果 ——
否则 `ABF-292-AI` 会被切成 `ABF-292` + `-AI`，拼出 `ABF-292-AI-AI.mp4`。

目录名自带的重复标记不会再加到文件名上：目录 `CLUB-880 (2)` 里的
`CLUB-880 (2).mp4` 保持原样，不会变成 `CLUB-880 (2) (2).mp4`。

### 目录里的别作作品，按它自己的番号规范化

一个目录里可能混着**别的作品**：`DVDMS-980/` 里放的是 A / B 两个变体，
文件名是 `hhd800.com@DVDMS-980-A.mp4`。

番号**不能**套目录的番号 —— `DVDMS-980-A` 是另一部作品，套成 `DVDMS-980`
会把变体信息抹掉。但水印域名是纯噪声，跟内容标识无关，该剥掉；番号本身
也该规范成厂牌-序号：

```
hhd800.com@DVDMS-980-A.mp4  ->  DVDMS-980-A.mp4
aavv38.xyz@STSK108A.mp4      ->  STSK-108A.mp4      （在 STSK-108/ 目录里）
```

剥完撞上已有同名文件 → **报冲突，绝不覆盖**（`OFJE-697/` 里就是这种情况：
水印版和干净版各存了一份，内容一致，只能靠人工确认后删掉其中一份）。

### 字幕要跟着视频走

`.srt` / `.ass` / `.ssa` / `.sub` / `.vtt` 也算媒体扩展名，参与 `archive` 分装。
不参与的话，顶层平铺的 `hhd800.com@DVDMS-977.mp4` 和
`hhd800.com@DVDMS-977.ja.srt` 会变成「视频进了目录、字幕留在顶层」——
两者分离，而且带水印的字幕名永远规范化不掉。

### 冲突判定与卷的大小写语义无关

这是最容易踩、也最不容易看出来的一类 bug —— **它不报错，只是静默不生效**。

exFAT / APFS（默认）/ NTFS 都是大小写不敏感的：
`CLUB-880.mp4` 和 `club-880.mp4` 指的是**同一个文件**，
所以 `Path.exists()` 对两者都返回 True。

实测 G 盘踩到的坑：目录名是 `club-880`（小写），文件名是 `CLUB-880.mp4`（大写）。
目录名规范化后文件的目标名是 `club-880.mp4`，而 `exists()` 判定「已存在」恒为真 ——
明明是同一个文件，却被判成**冲突**，于是文件名永远规范化不了。
（G 盘有 6 个这样的目录，全部卡住。）

正确判定靠**文件身份**（inode + 设备号，`os.path.samefile`），
不是路径字符串。「仅大小写不同」指的是**同一个文件** —— 那不是冲突，
是一次纯大小写改名，走两步（先挪临时名再改目标名）。

真正的冲突是「**另一个**文件占了目标名」。这种情况也不再「跳过」，
而是按**体积**分配：大的那份占着规范名，小的那份改名 ` (2)`，
**两份都留着，绝不覆盖**。

```
CLUB-806/CLUB-806C.mp4   1.19 GB   -> CLUB-806C.mp4      (让位)
CLUB-806/CLUB806C.mp4    2.23 GB   -> CLUB-806C.mp4      (占着规范名)
```

执行时有先后：占着规范名的那份要等让位的那份先挪走，否则改名会撞上。
所以 `apply_file_plan` 会先处理「目标名被别人占着、而那个人也在计划里改名」
的项，反复几轮直到没有进展 —— 剩下的才是真冲突。

同理，**验证改名结果也不能靠 `exists()`** ——
大小写不敏感卷上旧名和新名是同一个路径，要看 `iterdir()` 的列表。

#### 反过来也一样：Linux / macOS 大小写敏感分区上的漏判

Linux ext4、macOS 的**大小写敏感**分区上，`exists()` 对只差大小写的目标名
返回 **False**。而整理出来的库最终是要放到 exFAT 上的，那边
`club-810` 与 `CLUB-810` 是**同一个名字**：

```
club810  ->  CLUB-810     （统一大写之后，两边得到同一个目标名）
CLUB810  ->  CLUB-810
```

在大小写敏感的卷上，`exists()` 说「没被占用」，改名成功；
等库拷到 exFAT，两个只差大小写的文件就撞了 —— exFAT 根本放不下。

**统一大写把这个问题从根上消掉**：规范名只有一种写法（`uppercase: true`），
两个只差大小写的输入收敛到同一个目标名，不会产生「两个只差大小写的目录」。
这比「算准了再报冲突」更彻底 —— 冲突判据依赖的是**目标名**，
而统一大小写之后目标名根本不会只差大小写。

所以占用判定照样**自己算**，永远忽略大小写：
`fscompat.colliding_entries(目录, 目标名)` 扫出目录里所有「忽略大小写后
与目标名相同」的条目。`rename` / `rename-files` / `archive` / `isolate` /
`merge` 五处全都走它，不问文件系统。

这样同一个库在 exFAT、ext4、大小写敏感的 APFS 上整理出的结构完全一致。

> CI 里怎么守住：NTFS 支持**目录级大小写敏感**（WSL 用的就是它），
> Windows runner 上用 `fsutil file setCaseSensitiveInfo` 开一个这样的目录，
> 再把 pytest 的 `--basetemp` 指进去跑一遍 —— 不用额外的 POSIX runner
> 就能验出这一类 bug。见 `.github/workflows/ci.yml`。

#### 纯大小写改名不算冲突

「目标名就是源自己、只差大小写」是**纯大小写改名**，不是冲突：

```
avop-235-C  ->  AVOP-235-C
```

规划阶段必须把这两件事分开：

- 目标名对应的位置上**只有源自己** → 纯大小写改名，走两步 rename
- 旁边还**站着另一个条目**（大小写敏感的卷上 `avop-235-C` 与 `AVOP-235-C`
  能同时存在） → 真撞名

区分这两者需要**保留重数**的索引 —— 只记「这个名字存在吗」是不够的，
「存在的是不是它自己」才是关键。

统一大写之前这条判断用不上（规则模板只做原样插值，产不出纯大小写变化的
目标名），统一大写之后每个小写厂牌的目录都会走到这一步。

#### 占用判定用的是内存索引，不是反复列目录

`colliding_entries` 每次调用都要列一遍目录，逐条查就是 **O(n²)**。
批量改名时改成**建一次索引、之后按键查**，改名后同步更新索引
（腾出来的名字后面还要能用）。实测 3000 个顶层目录：
14.4 秒 → 0.33 秒。

索引是快照，所以真正改名之前还有一道「以磁盘为准」的兜底 ——
索引建好之后被别的进程占掉的目标名，以磁盘为准，绝不覆盖。

### 安全语义

- 扩展名原样保留（`.srt` `.jpg` `.mp4` 一视同仁，不做白名单）
- 目标已存在且不是同一个文件 → 报冲突，**绝不覆盖**
- 大小写不敏感的文件系统（exFAT / APFS 默认）上，仅大小写不同的改名走两步，
  否则 `rename` 会「无事发生」
- 资源叉 `._xxx` 跳过（由 `clean` 负责）

## 两阶段：先改名，再合并

```
阶段 1  rename（纯文本，规则驱动，毫秒级）
        aavv38.xyz@SDMM028    -> SDMM-028
        SDMM030AC(1)          -> SDMM-030AC (1)

阶段 2  merge（内容比对，IO 密集）
        按「基础名」分组 -> 逐组比对文件指纹 -> 判定能否合并
```

两个阶段故意分开：改名几乎无损，合并会删目录，风险等级不同，不该藏在同一个命令里。
merge 在改名**之后**运行，此时目录名已是规范名，分组更直观。

> `tidy` 把两个阶段串起来了，但**顺序是反的**：
> `clean → isolate → merge → archive → rename → rename-files`。
> merge 排在前面是因为合并后目录数减少，改名时的冲突检测更准。
>
> 两种顺序都能用 —— merge 的分组键会把尾部的 `(1)` 标记剥掉再解析，
> 所以改名前（`DVMM-055A (1)`）和改名后（`DVMM-055A (1)`）都能正确归组。
>
> 合并先跑还有个好处：`DVMM-055A (1)/` 里的文件叫 `DVMM-055A (1).mp4`，
> 和主目录的 `DVMM-055A.mp4` **不撞名**，两个压制版本可以和平共处。

## merge 的判定依据：内容，不是名字

**目录名带 `(1)` 不代表是复制副本。** 实测 `/Volumes/P7000Z/R` 的 10 组候选：

| 分组 | 结论 | 实情 |
|---|---|---|
| `SDMM-030AC` | DUPLICATE | mp4 大小完全相同 → 真副本 |
| `TEA-240808-24` | DUPLICATE | 13 个文件路径+大小全等 → 真副本 |
| `TEA-240808-30` | DUPLICATE | 246951522 = 246951522 → 真副本 |
| `SDMM-030BC` | DIFFERENT | 封面相同，mp4 差 4 倍 → **不同画质版本** |
| `SDMM-076` | DIFFERENT | 封面相同，mp4 5.1GB vs 6.3GB → **不同画质版本** |
| `DVMM-055A` | DIFFERENT | 封面相同，mp4 3.8GB vs 4.1GB → **不同画质版本** |
| `DVMM-055B` | DIFFERENT | 封面相同，mp4 639MB vs 5.6GB → **不同画质版本** |
| `HEA-240609-02` | PARTIAL | 32 个 vs 52 个文件 → 部分重叠 |
| `FLUP-11223` | PARTIAL | 3 个目录各 6 个**完全不同**的文件 → 分P |
| `DOW-240722-05` | PARTIAL | `01/` 装 1-10.mp4、`02/` 装 11-14.mp4 → **分P** |

只看名字就合并会**直接销毁数据**（7/10 的组会丢文件）。所以判定必须看内容。

### 三种判定

判定结果**只用来描述内容关系**，不再决定「能不能合」：

- `DUPLICATE` —— 内容完全一致
- `DIFFERENT` —— 同名文件内容冲突 → 不同画质版本
- `PARTIAL` —— 部分重叠 → 既有重复也有独有文件

### 执行语义：一律合并，两份都留着

默认**一律合并**基础名相同的目录 —— 保留一个主目录，其余目录的文件挪进去。

合并时逐个文件处理，**任何一种情况都不丢数据**：

| 情况 | 处理 |
|---|---|
| **内容相同**（不论文件名是否相同） | 只留一份，删掉副本那份 |
| 目标名没被占 | 移动过去 |
| 目标名被占但内容不同 | 按**体积**分配：大的占规范名，小的改名 ` (2)` |

「按体积分配」的理由：这类冲突几乎都是**同一部片子的不同压制版本**。
实测 `CLUB-806/` 里 `CLUB-806C.mp4`（1.19 GB）和 `CLUB806C.mp4`（2.23 GB）
规范化后指向同一个名字 —— 大的那份通常是画质更好的版本，让它占着规范名
是合理的默认，小的改名 `CLUB-806C (2).mp4`，**两份都留着**。

体积相等时，已经就位的那份优先留下，进来的那份让位 —— 「不动已经就位
的东西」更保守。

内容去重不看文件名：实测 `DVMM-055A` 与 `DVMM-055A (1)` 里的封面 jpg
是字节一致的两份，合并后只该留一份。

保守模式（`--keep-separate`）下只合并 `DUPLICATE` 组，内容不同/部分重叠
的组各自保留 —— 这是给「不确定能不能并」时留的退路，不是默认行为。

> **合并发生在改名之前**（tidy 的编排：clean → isolate → merge → archive
> → rename → rename-files）。目录名还是原始形态时分组更直观；而且
> `DVMM-055A (1)` 里的文件叫 `DVMM-055A (1).mp4`，和主目录的
> `DVMM-055A.mp4` **不撞名**，两个压制版本可以和平共处。

### 指纹算法

文件指纹 = 大小 + 首尾各 1MiB 的 sha256。不用全量哈希是因为视频动辄几十 GB；
首尾+大小足以区分不同片源。`._xxx` 资源叉文件和 `.DS_Store` 不参与比对。

## 规则文件

规则全部写在 `rules/numbering.yaml`，分三段：

```yaml
exclude:           # 永不视为番号的名称形态（国产编号前缀）
  - '^FLUP[-_]?\d'

uppercase: true    # 规范名统一大写（厂牌 + 序号 + 版本后缀）

preprocess:        # 噪声剥离（与番号知识无关）
  - name: strip_watermark_domain
    pattern: '^(?P<domain>...\.xyz)@'
    capture: domain        # 捕获组名须存在于 pattern 中，否则加载报错

matches:           # 番号匹配（领域知识），按 priority 降序尝试
  - name: studio_dash_num
    pattern: '^(?P<studio>[A-Z]{2,6})-(?P<num>\d{2,6})(?P<ver>[A-Z]{0,3})$'
    template: '{studio}-{num}{ver}'       # 用命名分组回填；{raw} = 剥离后原串
    dup_suffix: ' ({dup})'               # 重复副本标记的回贴方式
    priority: 90
```

合成结果 = `template` 回填 + `dup_suffix` 回贴。

### 规范名统一大写

`uppercase: true`（默认）时，规范名里的厂牌、序号、版本后缀一律大写：
`avop-235-C` → `AVOP-235-C`、`dvdms00300a` → `DVDMS-00300A`、
`kin8-3980` → `KIN8-3980`。

**为什么必须统一**：整理出来的库最终是要放到 exFAT 上的，而 exFAT / NTFS /
macOS APFS（默认）全都大小写不敏感 —— 在它们上面 `club-810` 与 `CLUB-810`
是同一个名字。在大小写敏感的卷（Linux ext4）上整理出来的库，两个只差大小写
的目录能共存；拷到 exFAT 上就撞了。统一大写把这个问题从根上消掉，而不是
留给「拷贝时报错」。

**只作用于规范名本身**：

- 扩展名原样保留（`.mp4` 不动）—— 刮削器和播放器对扩展名大小写敏感的地方
  不少，改它收益为零、风险不小
- 噪声后缀原样保留（`_en` / `[4K]` 这类标记是有意义的信息）
- 中文标题文件一律不动 —— 那些名字是内容标识，不是番号

**大写发生在噪声剥离之后**：剥离规则里有好几条是靠「域名小写、番号大写」
把两段切开的。先大写，这三种形态全部切不开：

```
dxxdom.comSONE815        -> SONE-815       ✓
DXXDOM.COMSONE815        -> 解析失败       ✘
SDMM128Caavv38.xyz@      -> SDMM-128C      ✓
SDMM128CAAVV38.XYZ@      -> 解析失败       ✘
```

所以实现上，大写加在**引擎渲染出规范名的那一步**，噪声剥离一个字都不动。

### 条件剥离规则

`conditional: true` 的预处理规则**只在基准匹配不上时才尝试**。
这是为了区分两种同形的横杠：

- `MAAN961-2` 的 `-2` 是重复副本标记 → 该剥
- `MAAN-961` 的 `-961` 是番号本身 → 不能剥

两者字形相同，只能靠「剥完是否仍是合法番号」区分。

**注意「只在基准匹配不上时」这个前提。** 如果基准已经能正确解析，
却允许剥离结果覆盖它，就会把规范名改坏 —— 实测踩过：
`DOW-240706-24` 本身能被日期型规则正确解析，而剥掉 `-24` 后剩下的
`DOW-240706` 会被「厂牌-数字」规则抢先匹配，改成 `DOW-240706 (24)`。
（这条 `date_style` 规则后来因为日期型整体是国产编号而删掉了，
但**引擎逻辑的修正保留** —— 将来加新规则时不会再踩同一个坑。）

### 重复副本标记

`dup_sources` 决定 `{dup}` 槽位的取值优先级（默认 `["dup", "wdup"]`）。
`dup` 来自目录名尾部（`(1)` / ` 2` / `-2`），`wdup` 来自水印域名内部（`aavv38(1).xyz@`）。

标记会被回贴成 ` (1)` 形式，避免与主目录撞名：

```
aavv38.xyz@DVMM055A      -> DVMM-055A
aavv38(1).xyz@DVMM055A   -> DVMM-055A (1)
```

### 排除名单：哪些形态根本不是番号

```yaml
exclude:
  - '^FLUP[-_]?\d'
  - '^(?:DOW|TEA|LRO|HEA|KEO|7K|WLF|DEL|XZO)[-_]?\d'
  - '^(?:MON|xfxfz)[-_]?\d'
```

命中排除的名字**直接判为不符合规范，不再下探内容判定**。这一步的顺序很重要：
国产目录里全是原始导出名（`image_2023` / `photo_2023` / `IMG_7847` / `dw9358`），
宽松的番号正则会把它们误认成番号，导致国产内容被留在番号库里 —— 实测会误伤 32 个目录。

排除是「整类形态」的判断，必须写在规则文件里而不是代码里 ——
哪个前缀属于国产是领域知识，会随资料来源变化。

**排除一律忽略大小写**（实现上用 `re.IGNORECASE`，规则文件里不用写 `(?i)`）。
国产编号的写法本身就没有大小写规范 —— `xfxfz14468` 和 `XFXFZ14468` 是同一个站
的同一种编号。如果排除是大小写敏感的，那么「规范名统一大写」之后，
国产内容会因为「变成了大写形态」而不再命中排除 —— 正好和这次改动的目标相反。

实测修正前后：

```
xfxfz14468   -> 排除 ✓     XFXFZ14468   -> 修正前当成番号 XFXFZ-14468  ✘
mon004       -> 修正前当成番号 ✘   MON004  -> 排除 ✓
```

以前这份列表在 5 条规则里各抄一遍，抄漏一个就有一条规则认不出那种域名。
实测踩过：`wbrr.life@ADN-683CX.mp4` 因为 `.life` 没抄进去，剥不掉域名，
文件名就一直规范化不了。**加后缀只改 `engine.py` 一处。**

**加新规则后必须全库跑一遍预览，确认破坏数为 0** ——
新规则可能抢在旧规则前面匹配，把已经规范的目录改坏。
`tests/` 里有幂等性测试兜底，但真库验证还是要自己跑。

### 导出名不是番号

判定「目录里有没有番号」用的是宽松正则，但**相机/手机的原始导出名**
长得像番号却不是番号：

```
IMG_6481.jpg     photo_2023.jpg     dw9358.jpg     P1000123.jpg
```

这些是导出工具的默认文件名（`IMG` / `DSC` / `DJI` / `photo` / `dw`…），
不是厂牌名。实测国产合集目录 `322` 里全是这类文件，宽松正则会把它们
认成番号 —— 结果整个国产合集被判成「含番号」而留在番号库里，
**国产内容就这么混进了番号库**。

所以 `isolate` 会排除已知导出前缀（见 `file_tool/isolate.py` 的
`_EXPORT_NAME_PREFIXES`）。真实的番号厂牌不会撞上这些前缀。

名单里还有 `Page0000` 这类扫描件/相册导出名 —— 实测一个国产相册目录里
全是 `Page0000.jpg` ~ `Page0027.jpg`，不排掉整个目录会被判成「含番号」。

### 中文标题里的番号形态不是番号

国产站爱给内容套一个番号形态的码，而且套在**中文标题里**：

```
【AI增强】SATM-035美少女模特为了凑医药费出卖肉体.mp4
…【XueNi-888】超高颜值妩媚动人小骚逼裸舞自慰喷水③.mp4
…DMX-0067.mp4      …TQ-00028.mp4      …AH-001.mp4      …BOI096.mp4
```

旧判定只看「名字里有没有番号形态的片段」，于是这批国产目录全被判成
「含番号的合集目录」留在原地 —— **国产内容就这么卡在番号库里，隔离不出去**。
实测一个国产下载夹 631 个子目录，旧判定只挪走 552 个，79 个被误判留下。

现在判定加了一条：**名字里含中日韩字符，就不算番号形态**。
真番号的文件名是纯 ASCII（`ABP-001.mp4` / `489155.com@CLUB-925.mp4`）。

这条收紧对番号库是**零影响**：实测 F / G / H 三个番号库，番号形态的命中名
372 / 417 / 306 条里，**含中日韩字符的有 0 条**；四个库 1318 个目录逐个比对，
判定翻转 0 个。

唯一的例外是**含中日韩字符的子目录名**：下载站会给目录起
「第一會所新片@SIS001@CLUB-936」这种复合名，名字带中文但确实是番号。
所以子目录名仍然交给规则集再判一次 —— 漏了这一步，合集目录会被误挪走。

**判定「目录里有没有番号」用的宽松正则要认版本后缀字母。**
`START-489V` 的 `V` 跟在数字后面，旧正则要求数字后紧跟非字母数字，于是
`START-489V.mp4` 匹配不上。这会导致**两道判定同时失手**：
目录名 `第一會所新片@SIS001@START-489V` 解析不出番号（缺规则），
目录内的文件名又认不出番号（缺后缀支持）——
一个**真番号目录**因此被当成国产内容挪进了 GC。

**名单是实测出来的，不是猜的。** 判定依据是**目录里有没有番号文件**：

| 前缀 | 目录数 | 含番号文件的 | 结论 |
|---|---|---|---|
| `DOW` / `TEA` / `LRO` / `HEA` / `KEO` / `7K` / `WLF` / `DEL` / `XZO` | 207 | 0 | 国产（日期型编号） |
| `MON` | 17 | 0 | 国产 |
| `xfxfz` | 53 | 0 | 国产 |
| `FLUP` | 488 | 0 | 国产 |

那 4 个「含番号文件」的 DOW 目录也是国产 —— 里面的 `SCN-0030.mp4` 是**别的作品**的番号。

### 日期型为什么从番号规则里删掉

「厂牌 + YYMMDD + 序号」（`DOW24070403`）是**国产资源站的目录编号格式**，不是番号形态。
规则文件里曾经有一条 `date_style` 规则把它当番号规范化，结果国产内容被塞进了番号库。

现在这条 match 规则被彻底删掉，只在 exclude 里留名单。原因是留着它是个**持续的风险源** ——
以后每次下载国产内容，`XYZ24070403` 都会被规范化进番号库，再挪一次。
删掉之后，新的国产前缀不会匹配任何番号规则，`isolate` 会直接按内容判定把它归位。

### 幂等性：规范名必须能被规则反解回自己

规则输出的是**规范名**，规范名必须能被同一套规则重新解析回自己，
否则第二次跑 `rename` 就会把已经整理好的目录改坏。实测踩过两个坑：

| 坑 | 现象 |
|---|---|
| 日期型规则只吃无横杠输入，却输出带横杠的 `DOW-240706-24` | 重新解析时被「厂牌-数字」规则抢先匹配，改成 `DOW-240706 (24)` |
| 小写厂牌规则只吃无横杠输入，却输出带横杠的 `xfxfz-14681` | 重新解析时可选分组没匹配上，渲染出 `xfxfz-14681None` |

（这两个案例的规则后来都改了，但**引擎逻辑的修正保留**。）

两处修法：

1. **条件剥离只在基准匹配不上时才尝试** —— 否则剥离结果会覆盖掉正确的解析。
   `MAAN-961` 与 `DOW24072205-2` 的区分不依赖这条：前者剥掉 `-961` 后剩下 `MAAN`
   匹配不上任何规则，剥离自然被拒绝；后者基准本来就匹配不上，剥离才有机会生效。
2. **未参与匹配的可选分组是 `None`，要渲染成空串** —— 否则得到字符串 `"None"`。

改完这两处后，全库重跑 `rename` 的**破坏数为 0**。改动任何一条 match 规则后，
请对全库跑一次 `rename` 预览确认这个数仍是 0。

1. **archive 把资源叉一起搬进了新目录** —— `shutil.move` 会带走 `._xxx`，

### 第二轮：FLUP 归位 + 文件名番号规范化

### 三块盘的共同教训

- **改规则后必须全库跑预览**，确认破坏数为 0。F / G / H 三块盘每次改规则都是这么验的。
- **`tidy` 单遍跑不完** —— 目录改名先于文件改名，文件的新名当时被旧目录名占着，
  第一遍必报「被占用/失败」，再跑一遍即收敛。
- **文件被占用是常态**。H 盘有两个目录改名报「拒绝访问」——
  连改成临时名都不行，但里面的文件能随便改名：说明是**目录句柄**被占。
  查下来是 11 个迅雷进程攥着下载目录的句柄。重试约 50 秒后句柄释放，改名成功。

## 安全设计

- 所有命令默认 dry-run，必须显式 `--apply` 才改文件
- 目标名冲突会报 `CONFLICT` 并跳过，绝不静默覆盖
- **目标名是否被占用一律忽略大小写判定**（不问文件系统的语义）——
  exFAT / ext4 / 大小写敏感的 APFS 上整理出的结构必须一致，
  否则库换个平台就撞名
- **规范名统一大写**（`uppercase: true`）—— 规范名只有一种写法，
  两个只差大小写的输入不会产生「两个只差大小写的目录」
- 落盘时若目标名已被占用，兜底加序号（`SDMM-028C (2)`）
- **纯大小写改名不算冲突** —— 目标名对应的位置上只有源自己时，
  走两步 rename（先挪临时名再改目标名）
- merge **只改目录结构，不删文件** —— 文件是移过去的，不是复制过去的；
  唯一会删的是「内容完全相同」的重复文件（只留一份）
- merge 执行时同名不同内容的文件**按体积分配**：大的占规范名，
  小的改名 ` (2)`，两份都留着，**绝不覆盖**
- merge 默认合并所有同名组，`--keep-separate` 才是保守模式
  （只合并内容完全一致的组）
- **排除名单忽略大小写** —— 否则统一大写会把国产内容洗成番号
- archive 不删除任何视频文件，归一只是合并进同一目录
- archive 遇到同名文件跳过不覆盖；`._` 垃圾默认清理，可 `--keep-forks` 保留
- isolate 遇到目标同名目录加序号不覆盖；目标在源内部直接拒绝
- isolate 命中排除名单的目录直接判为不符合规范，不做内容下探
- **isolate 的内容判定里，名字含中日韩字符的不算番号形态** ——
  国产站把番号形态的码套在中文标题里，那是伪装不是番号；
  含中日韩字符的**子目录名**例外，仍交给规则集判一次
- clean 只删 `._` 资源叉，真实文件和目录一律不动
- tidy 的 `loose` 形态**完全不动**，只报告
- tidy 不递归改嵌套层（第二层是原始标题，不是番号）
- rename-files 只改文件名里已有番号的文件，其余保持原样
- rename-files 的扩展名原样保留，不做白名单
- rename-files 遇到「文件名是别的番号」时，**按它自己的番号**规范化，
  不套目录的番号（套了会把变体信息抹掉）
- 规则文件里的正则会在加载时校验，非法正则直接报错而不是运行期才炸
- **文件被占用 / 无权限**：跳过这个文件、记成失败、继续处理下一个，
  不让整次操作中断在「并了一半」的目录上
- **Windows 非法文件名**（保留设备名、`:` 等非法字符、结尾的点/空格）：
  Windows 上不碰它并如实报告；macOS 上照常处理
- `--json` 模式下 stdout 上只有 JSON，不掺人看的提示
